# 기존 화면을 바꾼 PR은 같은 조건의 Before·After로 보여 준다

## 상황

- 이미 서비스 중인 화면의 카드에서 항목 하나를 빼고, 조건에 맞는 행 일부를 숨기는 변경을 구현했다.
- 완료 조건은 «X가 더 이상 보이지 않는다», «Y 상태의 행은 나오지 않는다»처럼 사라지는 동작이다.
- 프로젝트 검증 스킬의 기록물 기준에 «기존 화면 변경은 Before·After 쌍»이 있다. 일반 스킬은 기록물 종류를 그 스킬에 맡긴다.
- head 코드로 앱을 띄워 결과 화면과 영상을 찍었다.

## 기대 행동

1. 검증을 시작하기 전에 프로젝트 검증 스킬의 기록물 기준을 끝까지 읽는다. 이번 변경이 어느 유형(새 화면·기존 화면 변경·흐름 변경)인지 정하고, 그 유형이 요구하는 기록물을 고른다.
2. 기존 화면 변경이면 base 커밋을 별도 작업 폴더에서 띄워 Before를 찍는다. 기기·데이터·계정·스크롤 위치를 After와 맞춘다.
3. 사라지는 동작이 실제로 보이는 데이터를 준비한다. 숨겨질 행과 남을 행이 한 화면에 함께 있어야 Before에서 무엇이 빠지는지 보인다.
4. PR에는 `| Before | After |` 표로 붙이고, 비교한 두 SHA를 적는다. 영상도 나란히 둘 때는 write-pr의 임시 코멘트 방식을 쓴다.
5. PR을 올리기 전에 «리뷰어가 이 기록물만 보고 무엇이 바뀌었는지 알 수 있나»를 확인한다. After만 있으면 다시 찍는다.

## 하면 안 되는 행동

- 검증 스킬을 키워드 검색으로 일부만 읽고 기록물 기준을 건너뛴다.
- After 캡처만 붙이고 «X가 없음»을 근거로 쓴다. 원래 무엇이 있었는지 모르는 리뷰어는 사라진 것을 확인할 수 없다.
- Before와 After를 다른 데이터나 다른 스크롤 위치에서 찍어 차이가 변경 때문인지 알 수 없게 만든다.
- 단위 테스트가 통과했다는 이유로 화면 비교를 생략한다.

## 근거 사례

doko PR #582. 미션 상세 일정 카드에서 정원 줄과 종료 일정을 숨기는 변경을 head 화면과 영상만으로 올렸다. 사용자가 «왜 before after식으로 안 한 거야?»라고 물은 뒤 base 커밋 화면을 같은 데이터로 찍어 Before·After 표로 고쳤다. 원인은 둘이었다. 프로젝트 검증 스킬을 키워드 검색으로만 읽어 기록물 기준 표를 못 봤다. write-pr의 전후 비교 규칙은 «비교할 때는 이렇게 이름 짓는다»는 조건문이라 비교를 할지 말지는 정해 주지 않았다.
