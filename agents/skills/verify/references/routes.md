# 조건별 검증 방법

확인하려는 동작을 가장 직접적으로 보여 주는 방법을 고른다. 모든 방법을 실행할 필요는 없다. `implement`와 `verify`가 함께 사용하며 결과 판단과 코드 확인, 기존 결과 재사용은 [공통 검증 규칙](../../agent-loop/references/verification.md)을 따른다.

| 확인할 조건 | 방법 | 남길 근거 |
|---|---|---|
| 도메인 로직·서버·순수 함수 | 프로젝트의 기존 테스트 실행 | 어떤 조건을 검사했는지, 테스트 입력과 실행 결과 |
| API 응답·데이터 저장 | 로컬·개발 API에 요청 | 요청과 응답, 필요하면 저장된 데이터. 호출 대상과 권한도 확인 |
| 화면 상태·배치 | 브라우저·기기에서 직접 확인하거나 테스트 실행 | 화면, 재현 방법, 관찰 결과. 필요하면 캡처 |
| 화면 전환·다시 진입·시간에 따라 달라지는 동작 | 실제 조작이나 반복 실행할 테스트 흐름 | 조작 전 상태, 행동, 기대한 결과와 실제 결과. 시간에 따른 변화를 보여 줘야 하면 영상 |
| 사람이 적용해야 하는 마이그레이션 | 적용한 뒤 해당 환경에서 검사 | 적용 전에는 미검증으로 적고 사람이 해야 할 작업을 남김 |

## 테스트와 API로 확인하기

- doko 테스트는 `pnpm test <path>`로 실행한다. 이 명령이 테스트 DB를 준비하므로 vitest를 직접 실행하지 않는다.
- 기존 테스트가 해당 조건을 직접 확인하면 재사용한다. 새 테스트는 같은 문제가 다시 생길 위험과 반복 확인할 가치를 보고 작성한다. `verify`에서 새로 만들면 임시 테스트 환경에 두고 제품 코드는 고치지 않는다.
- DB 제약, 중복 처리, cascade는 사용이 허용된 실제 테스트 DB에서 확인한다. 스키마를 읽는 것만으로 충족 처리하지 않는다.
- API 요청은 입력과 응답의 status·body를 남긴다. 저장되는 조건이라면 DB의 해당 행도 읽어서 확인한다. 접속 대상과 DB 쓰기는 프로젝트 지침을 따른다. 쿠키나 토큰을 근거에 노출하지 않는다.

## UI와 변경 전후 비교

- 화면의 글과 배치는 직접 확인할 수 있다. 데이터 저장, 권한, 중복 방지는 화면 캡처만으로 증명하지 않는다.
- 사용자가 전후 비교를 요청했거나, 버그를 고쳤거나, 이번 수정 때문에 결과가 달라졌는지 확인해야 하면 같은 조건에서 base와 head를 실행한다. 그 외에는 변경 후 결과만으로 충분한지 보고 불필요한 base 환경이나 영상을 만들지 않는다.
- base에서도 조건을 만족하면 그대로 적는다. 사용자에게 보이는 결과를 유지하는 내부 리팩터링이라면 화면에 차이가 있어야 한다고 요구하지 않는다.
- 반복 실행할 web 테스트는 [Playwright 사용법](web-playwright.md), 앱 테스트는 [Argent 사용법](app-argent.md)을 읽는다. 한 번 직접 확인할 일을 위해 반드시 자동 실행 흐름을 만들 필요는 없다.

## 실패했을 때

- 실행은 정상이지만 약속한 결과가 나오지 않으면 미충족이다. 시간 초과도 기능에서 약속한 시간을 어긴 것인지, 도구나 환경 때문에 실행하지 못한 것인지 구분한다.
- 환경, 로그인, 도구 문제로 실행하지 못하면 실제 오류를 근거로 미검증을 남긴다. 일시적 오류의 원인을 확인했다면 제한적으로 재시도할 수 있다. 통과시키려고 assertion의 조건을 느슨하게 바꾸지 않는다.
- 한 방법으로 확인하지 못해도 영향받지 않는 조건은 계속 검증한다. 다른 방법으로 충분한 근거를 얻을 수 있으면 사용하고 실제로 무엇을 확인했는지 밝힌다.
