# verify

아직 확인하지 못한 조건을 검증하거나, 코드·환경이 달라진 결과를 다시 확인한다. `implement`가 필요한 검증을 이미 마쳤다면 이 스킬을 따로 부를 필요는 없다. 그대로 쓸 수 있는 기존 결과는 재사용한다.

시작할 때 [공유 규칙](../agent-loop/CONTRACT.md)과 [검증과 기록 방법](../agent-loop/references/verification.md)을 읽는다. 제품 코드, 티켓 상태, 이슈의 체크박스는 바꾸지 않는다. PR 생성, 커밋, push, 유료 리뷰, 머지도 하지 않는다.

## 확인할 대상 정하기

| 호출 | 확인할 조건과 코드 |
|---|---|
| `verify <N>` | 티켓의 완료 조건과 연결된 열린 PR |
| `verify --pr <PR>` | PR 본문의 `Fixes`·`Closes`로 연결된 티켓의 조건. 연결된 티켓이 없으면 PR에 적힌 검증 항목 |
| `verify` | 현재 diff와 사용자 요청. 조건이 명확하면 진행하고, 뜻을 새로 정해야 할 때만 확인 |

- `--base <ref>`: 비교할 코드를 지정한다. 기본은 PR의 base이며 `main`이라고 가정하지 않는다.
- `--no-before`: 변경 전 코드와 비교하지 않는다.
- `--app`: 확인할 앱이나 API 범위를 지정한다.
- `--no-publish`: PR을 고치지 않고 로컬 결과만 보고한다.

열린 PR이 없으면 실제 로컬 커밋 SHA로 결과를 보고한다. 새 PR은 만들지 않는다.

## 검증하고 결과 남기기

1. 최신 PR, 이슈, 기존 검증 결과를 읽고 해당 worktree를 찾는다. 커밋하지 않은 제품 코드 변경이나 다른 작업이 있으면 덮어쓰지 않는다. 원격 브랜치에 맞출 때는 [sync-worktree.sh](../agent-loop/scripts/sync-worktree.sh), 작업 폴더와 커밋을 확인할 때는 [check-worktree.sh](../agent-loop/scripts/check-worktree.sh)를 사용한다.
2. [verified-head.sh](scripts/verified-head.sh)로 기록한 커밋과 PR head가 같은지 확인한다. 최신 완료 조건과 환경, 사용자 요청을 보고 다시 확인할 항목을 정한다. 같은 커밋에서 유효한 결과를 이유 없이 다시 확인하지 않는다. 커밋이 달라진 `stale` 결과는 공통 검증 문서의 기준으로 재사용 여부를 판단한다.
3. 무엇을 보면 통과로 판단할지 정하고 [조건별 검증 방법](references/routes.md)에 따라 실행한다. 준비나 실행이 실패하면 이유를 확인하고, 영향받지 않는 조건은 계속 검증한다. 제품 버그는 재현 방법과 실제 실패 결과를 남긴다. 검증을 통과시키려고 제품 코드를 고치지 않는다.
4. [검증 근거 확인](references/quality-gates.md)에 따라 결과가 해당 조건과 코드, 환경을 설명하는지 확인한다. 직접 조작한 결과도 재현 방법과 실제 관찰 내용이 있으면 사용할 수 있다. 데이터 저장이나 권한처럼 화면만으로 알 수 없는 동작을 캡처 하나로 증명하지 않는다.
5. 실행 후 코드와 PR head를 다시 확인한다. [PR에 검증 결과 적기](references/publishing.md)에 따라 같은 검증 섹션을 갱신한다. 코드나 커밋이 바뀌었다면 이전 실행으로 그 변경까지 확인했다고 쓰지 않는다.

## 필요한 환경만 준비하기

- 순수 함수나 기존 테스트를 확인하는 데 브라우저와 base 서버까지 준비할 필요는 없다. 같은 코드와 입력에서 통과한 타입 체크도 재사용한다. 실행을 막는 오류는 기록하고, 영향 없는 검증은 계속한다.
- 버그 수정 전후를 비교하거나, 사용자가 비교를 요청했거나, 이번 수정 때문에 결과가 달라졌는지 확인해야 할 때 변경 전 코드도 실행한다. 변경 후 결과만으로 판단할 수 있으면 비교를 생략할 수 있다. 사용자가 요청한 비교를 못 했다면 남은 일로 적는다.
- 한 번 확인할 UI는 사용 가능한 브라우저·기기 도구로 직접 조작한다. 같은 문제가 다시 생길 위험이 크거나 사용자가 요청했을 때 반복 실행할 spec·flow를 만든다.
- 계속 사용할 검증 파일은 구현 작업에서 PR에 반영한다. 이 스킬에서 새로 만드는 파일과 설정은 임시 디렉터리나 이미 gitignore로 제외된 결과 폴더에 둔다. 저장소 설정, 의존성, ignore 파일을 고치는 작업까지 함께 진행하지 않는다.
- 서버나 worktree가 필요하면 [doko 검증 환경](references/environment.md), web 테스트를 반복 실행하려면 [Playwright 사용법](references/web-playwright.md), 앱 테스트를 반복 실행하려면 [Argent 사용법](references/app-argent.md)을 읽는다.
- 실행 중 문제가 생기면 [오류와 해결 방법](references/errors.md)에서 해당 증상을 확인한다.

DB 쓰기, 마이그레이션, 로그인, 캡처·영상 게시 권한은 프로젝트와 도구의 지침을 따른다. 환경 문제를 추측하지 말고 필요한 부분을 직접 확인한다.

## 결과 보고와 정리

요청된 모든 조건에 충족·미충족·미검증 중 하나를 적고 근거를 남긴다. 사용한 코드와 환경도 밝힌다. 자신이 시작한 서버와 녹화, 만든 임시 worktree만 정리한다. 수정이 필요한 항목은 `implement`로 이어갈 수 있도록 재현 방법과 함께 보고한다.
