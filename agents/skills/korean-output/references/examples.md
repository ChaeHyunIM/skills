# Before/After 예시 — 오적용 실패 사례 포함

각 예시는 「Before → 위반 → 고치면 안 되는 것 → After」 구조다. "고치면 안 되는 것"이 핵심이다 — 얼핏 고쳐야 할 것처럼 보이지만 고치면 뜻이 달라지는 지점을 짚는다.

## 예시 1 — 불수능 화법: 절차 질문에 배경부터 깔기 (구조 규칙)

사용자 질문: "이 마이그레이션 어떻게 적용해요?"

**Before:**
> 마이그레이션 적용에 앞서 먼저 이해하셔야 할 부분이 있는데, drizzle 의 마이그레이션 시스템은 journal 파일의 배열 순서를 기준으로 실행 순서를 결정하는 구조를 가지고 있어서, 파일명의 타임스탬프와 실제 실행 순서가 다를 수 있다는 점을 고려하셨을 때, 이번 마이그레이션의 경우에는 `pnpm db:migrate` 를 실행하시면 되는데, 그 전에 dev 환경인지 확인이 필요할 수 있습니다.

**위반:**
- 절차 질문에 배경 설명(journal 구조)부터 깔았다 — 유형 혼합.
- 한 문장에 연결어미 5개 — 결론("db:migrate 실행")이 문장 중간에 매장됐다.
- "확인이 필요할 수 있습니다" — 행동 지시가 명사화 + 헤지로 흐려졌다.

**고치면 안 되는 것:** "dev 환경인지 확인" 자체는 삭제 대상이 아니다. 실행 전 필수 조건이므로 절차의 1단계로 승격해야 한다.

**After:**
> `pnpm db:migrate` 를 실행하면 됩니다. 실행 전에 타깃이 dev DB 인지 확인하세요.
>
> 참고로 실행 순서는 파일명 타임스탬프가 아니라 journal 배열 순서를 따릅니다.

배경은 삭제가 아니라 분리다 — 이 사용자의 기대(타임스탬프 순서)와 어긋나는 사실이므로 "참고로" 절로 남긴다.

## 예시 2 — 헤지 승격: 이 카탈로그의 가장 흔한 오적용 (안전핀)

**Before:**
> 이 문제는 renditions_ready 플래그가 백필 시점에 갱신되지 않았을 가능성이 있다는 점을 고려했을 때, 우선 해당 컬럼의 상태를 확인한 후에 필요하다면 재실행을 진행하는 것이 좋을 것으로 보이는데, 다만 이 경우에도 idle 로 되돌리는 작업이 선행되어야 한다는 점은 유의할 필요가 있습니다.

**위반:**
- 연결어미 4개, 한 문장에 판단 3개.
- "재실행을 진행" — 명사화.
- "유의할 필요가 있습니다" — 메타 담화.

**고치면 안 되는 것:** "갱신되지 않았을 가능성" — 아직 확인 전이므로 헤지가 정확한 보고다.

**After:**
> renditions_ready 가 백필 때 갱신되지 않았을 수 있습니다. 먼저 컬럼 상태를 확인하세요. 재실행하려면 idle 로 되돌린 뒤 실행해야 합니다.

**실패 사례:** 이 문장을 "renditions_ready 가 백필 때 갱신되지 않았습니다. 재실행하세요." 로 줄이면 더 잘 읽히지만 틀렸다. 첫 문장은 시스템이 추측만 하는 실패를 단정했고, 확인 단계를 삭제해서 불필요한 재실행(비용 발생)을 유도한다. 짧고 매끄러운 재작성이 원문에 없는 확실성을 만들면 그건 재작성이 아니다.

## 예시 3 — 번역투·명사화 (문장 규칙 + 카탈로그)

**Before:**
> 이미지 업로드에 대한 처리가 완료된 이후에, 해당 파일의 메타데이터를 통해 렌디션 생성 작업이 자동으로 진행되어지게 됩니다.

**위반:**
- "~에 대한 처리가 완료된 이후에" → 명사구 직역 (카탈로그 2, 9).
- "~를 통해" (카탈로그 3).
- "해당 파일" — 대명사 남발 (문장 규칙).
- "진행되어지게 됩니다" — 명사화 + 이중 피동 (카탈로그 1, 7).

**고치면 안 되는 것:** "자동으로" — 사용자 행동이 필요 없다는 정보이므로 유지한다.

**After:**
> 이미지를 업로드하면 파일 메타데이터로 렌디션이 자동 생성됩니다.

## 예시 4 — 과잉 비계: 이미 아는 용어를 되짚기 (구조 규칙)

사용자 질문: "RQ 캐시가 stale 인데 invalidate 가 안 먹는 것 같아요."

**Before:**
> React Query 는 서버 상태를 캐싱하는 라이브러리로, 각 쿼리는 queryKey 로 식별됩니다. invalidateQueries 를 호출하면 해당 키의 캐시가 stale 로 표시되고 refetch 가 일어나는데, 이때 queryKey 가 정확히 일치해야 합니다. 지금 문제는 mutation 쪽 키가 `['posts']` 인데 조회 쪽이 `['posts', filter]` 라서...

**위반:**
- 사용자가 이미 "RQ", "stale", "invalidate" 를 썼다 — 그 개념 설명은 전부 소음이다. 스키마가 있는 독자는 설명과 자기 지식을 대조하는 데 작업기억을 쓰고, 그 대조는 아무것도 산출하지 않는다.
- 진짜 답(키 불일치)이 세 문장 뒤에 있다.

**고치면 안 되는 것:** queryKey 불일치의 구체 좌표(`['posts']` vs `['posts', filter]`)는 유지한다 — 이게 답변의 전부다.

**After:**
> invalidate 는 먹고 있는데 키가 안 맞습니다. mutation 쪽은 `['posts']`, 조회 쪽은 `['posts', filter]` 라서 무효화 대상에서 빠집니다. mutation 의 invalidateQueries 에 `{ queryKey: ['posts'], exact: false }` 를 쓰거나 키를 맞추세요.

**반대 방향도 위반이다.** 여기서 아끼는 것은 «사용자가 이미 쓴 용어»의 재설명뿐이다. 내가 처음 꺼내는 것 — 이 답변에서라면 `exact: false` 같은 옵션 — 은 한 문단으로 푼다:

> `exact: false` 는 키의 앞부분만 맞아도 무효화하는 접두사 매칭입니다. `['posts']` 를 주면 `['posts', filter]` 도 같이 털립니다.

새 개념을 푸는 것과 아는 개념을 되짚는 것은 정반대 동작이다. 전자를 아끼면 답변이 짧아지는 게 아니라 사용자가 되묻는다.

## 예시 5 — 결론 투하 vs 과정 덤프: 양극단이 같은 병 (구조 규칙)

작업: 버그 원인을 찾아 수정함.

**Before (결론 투하):**
> 고쳤습니다.

**Before (과정 덤프):**
> 먼저 HomeScreen.tsx 를 확인했고, 문제가 없어 보여서 useHomeFeed.ts 를 읽었습니다. 여기서 select 콜백을 의심했지만 아니었고, 다음으로 FeedList.tsx 의 렌더 로직을 추적한 결과 keyExtractor 가... (12문장 계속)

**위반:** 둘 다 상대의 필요를 모형화하지 않고 자기 머릿속 상태를 그대로 출력했다. 전자는 검증 수단을 안 줬고, 후자는 기각된 가설(독자에게 쓸모없는 정보)로 외재적 부하를 얹었다.

**고치면 안 되는 것:** 과정 덤프를 줄일 때 "왜 이 수정이 맞는지"의 좌표까지 지우면 결론 투하가 된다.

**After:**
> 고쳤습니다. 원인은 FeedList.tsx:41 의 keyExtractor 가 index 를 쓰고 있어서, 목록이 갱신될 때 아이템이 재사용된 것입니다. id 기반으로 바꿨습니다.

주장(원인)마다 좌표 1개, 기각한 가설은 0개. 사용자가 탐색 과정을 물으면 그때 푼다.

## 예시 6 — 메타 담화 vs 선행 조직자: 삭제 테스트 (구조 규칙)

긴 분석 답변의 첫 문장.

**Before:**
> 지금부터 이번 장애의 원인과 대응 방안에 대해 순서대로 정리해서 말씀드리겠습니다.

**위반:** 삭제 테스트 실패 — 이 문장을 지워도 독자가 잃는 정보가 없다. "말에 대한 말"이다.

**고치면 안 되는 것:** 지도를 주는 것 자체는 좋다. 긴 답변 앞의 조직자는 유지하되, 명제를 담게 고친다.

**After:**
> 장애 원인은 Hyperdrive 캐싱이고, 대응은 두 갈래입니다 — 즉시 조치(캐싱 비활성화)와 재발 방지(write-after-read 패턴 제거).

같은 자리, 같은 역할(지도)이지만 이 문장은 지우면 결론을 잃는다. 조직자와 메타 담화의 차이는 어미가 아니라 문장이 명제를 담느냐다.
