# html-style

HTML로 만드는 보고서, 제안서, 계산기를 읽고 쓰기 쉽게 만드는 규칙이다. Claude Code에서는 `/html-style`, Codex에서는 `$html-style`로 사용자가 직접 부를 때 적용한다.

사용자가 원하는 디자인을 따로 말하면 그에 따른다. 별도 요청이 없을 때는 아래 규칙을 쓴다. 새 페이지는 전체 구성을 잡고, 기존 페이지의 작은 수정은 필요한 부분만 고친다. 스타일을 고쳐 달라는 요청에 게시까지 포함돼 있다고 가정하지 않는다.

폰트와 색, 간격의 기본 규칙은 Vercel의 `design.md`와 공개 CSS(2026년 9월 기준)에서 가져왔고, 폰트는 Pretendard로 바꿨다. 우리 페이지를 검토하다 추가한 규칙에는 당시 날짜와 페이지, 문제가 된 부분을 함께 적는다.

## 누가 왜 읽는지 먼저 정하기

독자가 무엇을 알고 싶거나 결정해야 하는지 먼저 파악한다. 자료가 뒷받침하는 답을 찾고, 그 답을 믿을 만한 근거를 붙인다. 아직 알 수 없는 점이나 결론이 달라질 수 있는 조건도 남긴다.

훑어봐도 요점을 알 수 있고, 자세히 읽으면 근거를 확인할 수 있게 쓴다. 제목과 중요한 숫자, 표·그림의 설명만 읽어도 내용을 따라갈 수 있어야 한다. 정확한 용어와 수치, 계산에 쓴 가정과 방법, 출처는 자세히 읽는 사람이 확인할 수 있는 곳에 둔다.

여러 규칙을 한꺼번에 지키기 어렵다면 다음 순서로 판단한다.

1. 받은 자료의 사실과 숫자를 바꾸지 않는다. 단위와 기간, “추정”, “최대” 같은 표현도 빠뜨리지 않는다.
2. 독자의 질문에 대한 답과 근거가 쉽게 보이게 한다.
3. 자료를 가장 잘 설명하는 구성을 고른다. 문서 종류만 보고 늘 같은 틀을 쓰지 않는다.
4. 작은 화면에서도 읽기 쉽고, 버튼과 입력창이 제대로 작동하게 다듬는다.

의도, 긴급성, 확신의 정도, 마감, 승인 여부, 고객 이름, 가격이나 숫자를 지어내지 않는다. 자료에 없으면 생략하거나 “미정”이라고 쓴다.

자료끼리 내용이 다르면 출처와 기간, 단위, 용어의 뜻을 먼저 확인한다. 차이를 설명할 수 있으면 구분해서 적는다. 결론에 영향을 주는 차이가 끝내 설명되지 않을 때 사용자에게 묻는다. 답을 기다리는 동안 나머지 작업은 계속한다.

## 문장과 제목 쓰기

독자는 대개 비개발자다. 동료에게 설명할 때 쓸 법한 말로 쓴다. 영어를 직역한 표현이나 뜻을 짐작해야 하는 추상적인 말은 구체적으로 풀어 쓴다. “비색 단서”보다는 “색의 의미를 글자나 기호로도 표시한다”가 낫다.

- 문장을 줄이려고 명사만 나열하지 않는다. 본문은 무엇을 설명하거나 해야 하는지 알 수 있는 완전한 문장으로 쓴다. 버튼이나 그래프 축의 이름은 짧게 써도 된다.
- 실제 코드, 식별자, 수치는 그대로 쓴다. 설명에 불필요한 영어 이름을 붙이지 않는다.
- 페이지 제목과 소제목에는 내용을 담고 명사형으로 끝낸다. “개요”, “일정”처럼 문서 분류만 적지 않는다. “리뷰에서 찾은 세 가지”, “빠져 있는 한 조각, 일본어 CS”처럼 쓴다.
- 한국어 보고서의 제목에 “~합니다”를 쓰지 않는다. 단, 누가 무엇을 약속하는지 드러내야 하는 문장은 한 번 쓸 수 있다. 예: “이번 메가와리부터 유어케이스가 채운의 일본 운영팀이 되겠습니다”.
- 일본어나 중국어를 인용한 요소에는 각각 `lang="ja"`, `lang="zh"`를 붙인다. 줄바꿈을 그 언어에 맞게 처리하기 위해서다.
- 페이지 안에 “이 내용을 이렇게 구성했다” 같은 제작 과정 설명을 넣지 않는다.

제목을 명사형으로 쓰는 규칙은 2026-09-10 Chaewun 일본 제안에서 추가했다. “~합니다”로 끝나는 제목이 발표 대본처럼 읽혔기 때문이다. 제목에 관한 규칙이며, 본문까지 명사형으로 끊어 쓰라는 뜻은 아니다.

## 첫 화면과 본문 구성하기

첫 화면만 봐도 가장 중요한 결론이나 차이를 알 수 있어야 한다. 계산기라면 첫 화면에서 바로 쓸 수 있어야 한다. 자료에 따라 다음과 같이 시작할 수 있다.

| 전달할 내용 | 첫 화면에 놓을 것 |
|---|---|
| 추천이나 결론 | 결론과 그 근거를 나란히 놓는다. |
| 여러 대안의 비교 | 같은 항목끼리 나란히 놓아 차이를 보여준다. |
| 시간에 따른 변화나 기준값과의 비교 | 눈에 띄는 변화나 예외를 먼저 보여준다. 정확한 수치는 아래 표에 정리한다. |
| 계산기나 도구 | 바로 조작할 수 있는 도구를 먼저 둔다. 긴 설명을 앞에 붙이지 않는다. |
| 결정을 요구하지 않는 현황 공유 | 중요한 현황과 그 의미, 아직 답하지 못한 질문을 보여준다. 자료에 없는 행동을 요청하지 않는다. |

컴포넌트를 고르기 전에 무엇을 어떤 모양으로 보여줄지 정한다.

| 보여줄 내용 | 표현 방법 |
|---|---|
| 크기나 순위의 차이 | 같은 기준으로 잰 길이나 위치를 비교한다. |
| 시간에 따른 변화 | 시간 순서대로 가로로 배치한다. |
| 전체에서 차지하는 비중 | 각 부분의 비율이 드러나게 한다. |
| 기준값이나 허용 범위와의 차이 | 기준선에서 얼마나 떨어져 있는지 보여준다. |
| 순서가 있거나 앞 단계에 달린 작업 | 단계의 순서와 연결을 보여준다. |
| 숫자로 비교하기 어려운 대안 | 같은 항목끼리 표의 행이나 열에 맞춰 놓는다. |

정확한 값을 찾아봐야 하면 표를 쓴다. 결론 하나는 문장으로 설명한다. 그래프는 변화나 차이를 더 빨리 이해할 수 있을 때 쓴다. 숫자가 있다는 이유만으로 막대그래프를 만들지 않는다.

단락마다 새로운 질문에 답한다. 같은 결론을 요약, 그래프, 카드, 마지막 문단에서 반복하지 않는다. 같은 주장을 뒷받침하는 자료는 한곳에 모은다.

대강 훑어봐도 가장 중요한 내용이 먼저 눈에 들어와야 한다. 모든 부분이 똑같이 강조돼 있으면 무엇을 먼저 읽게 할지 다시 정한다. 자료가 부족하면 설명과 순서를 고친다. 카드, 테두리, 아이콘, 색이나 장식용 그래프로 빈자리를 채우지 않는다.

마지막에는 결론, 다음 행동, 아직 결정하지 못한 질문 중 자료에 맞는 것을 적는다. 표나 주의사항만 나열하다 끝내지 않는다.

## 폰트와 색, 배치 정하기

폰트 크기와 굵기, 줄 간격, 여백, 색은 제공된 CSS 클래스를 골라 맞춘다. `font-size`, `font-weight`, `margin` 값을 그때그때 만들어 넣지 않는다. 페이지에 꼭 필요한 배치는 `vbg-custom-*` 클래스와 미리 정해 둔 CSS 변수로 만든다.

**폰트는 Pretendard Variable만 쓴다.** 제목과 본문에 맞는 클래스를 골라 중요도를 구분한다. 폰트가 파일에 들어 있으므로 외부 폰트 링크나 다른 폰트를 추가하지 않는다.

**색은 의미가 있을 때만 쓴다.** 먼저 흑백으로 내용을 구분하고, 상태나 행동, 데이터의 차이를 알릴 때 색을 더한다. 색의 의미는 글자나 기호로도 표시한다. 유리한 숫자라는 이유만으로 초록색을 칠하지 않는다. 라이트·다크 모드는 CSS가 처리하며, 페이지에 전환 버튼을 따로 만들지 않는다.

**내용을 카드로 잘게 나누지 않는다.** 페이지 전체가 이어져 보이게 한다. 카드는 선택한 항목이나 경고를 표시할 때, 또는 간격만으로는 함께 읽어야 할 내용을 묶기 어려울 때 쓴다. 단락이나 숫자마다 카드를 붙이지 않는다. 배경색으로 한 부분을 크게 강조해야 한다면 `.vbg-band[data-tone="contrast"]`를 한 곳에만 쓴다.

**아이콘은 행동을 알아보기 쉬울 때만 쓴다.** 닫기, 검색, 외부 링크처럼 익숙한 모양이 도움이 되는 경우에 Phosphor SVG를 쓴다. 장식용 아이콘은 넣지 않는다. 이모지는 브라우저 탭에 보이는 아이콘인 favicon에만 쓸 수 있다.

**로고는 원본 그대로 쓴다.** 로고나 글자로 된 로고를 data URI로 넣고, 색을 바꾸거나 마스크·필터를 씌우지 않는다. 너비는 원본 페이지에서 쓰던 값을 따른다. 다크 모드에서 잘 보이지 않으면 사용자에게 알리고 다크 모드용 로고가 있는지 묻는다.

**본문 링크는 링크처럼 보이게 한다.** `<a class="vbg-link">`를 쓰고 버튼 모양으로 꾸미지 않는다. 원문이 있으면 해당 단락 끝에 “원문: <링크>”를 붙인다.

**기본적으로 움직임을 넣지 않는다.** 스크롤할 때 나타나기, 깜빡이기, 가로로 흘러가기, 타이핑 커서, 마우스를 올렸을 때 움직이기 같은 효과를 넣지 않는다.

이미지와 설명을 카드로 묶을 때는 [이미지와 설명을 함께 배치하는 방법](references/image-caption-card.md)을 읽는다.

## 피해야 할 표현과 모양

사용자가 특히 거부한 네 가지다. 반드시 뺀다.

1. 배경에 빛이 둥글게 번지는 장식 효과.
2. 점이 깜빡이는 “Live” 상태 표시.
3. 제목 위에 작은 대문자를 놓고 글자 간격을 넓힌 장식 문구.
4. 카드 왼쪽의 색 세로선.

나머지는 아래 항목별로 확인한다.

| 종류 | 피해야 할 것 |
|---|---|
| 글자 | 작고 흐린 회색 본문, 임의로 정한 글자 크기, 나란히 비교하는 값의 서로 다른 크기·굵기·줄 위치. |
| 제목 장식 | 제목 위에 붙이는 불필요한 작은 문구, 단락 앞의 장식용 번호. 긴 대시(—)는 쉼표·마침표·괄호로 바꾼다. |
| 배경 장식 | 장식용 그라디언트와 그라디언트 글자, 빛 번짐, 둥근 덩어리, 줄무늬, 질감, 유리처럼 보이는 효과, 장식 그림자와 가짜 입체감. |
| 카드와 테두리 | 가운데 큰 제목을 놓고 그 아래 카드를 나열하는 뻔한 구성, 숫자마다 붙인 상자, 카드 안의 카드, 중요도를 구분하지 못한 채 테두리만 더하기. |
| 짧은 문구 | 날짜 같은 문서 정보나 차트 설명을 둥근 배지나 알약 모양으로 감싸기. |
| 아이콘과 이미지 | 아이콘을 담은 장식용 사각형, 지나치게 큰 아이콘, 서로 다른 스타일의 아이콘, 스톡 이미지, 가짜 스크린샷, 장식용 브랜드 로고. |
| 표 | 넓은 공간 안에 표만 좁게 두기, 표를 압축해 단어가 중간에서 끊기게 만들기. |
| 그래프 | 같은 내용을 여러 그래프로 보여주기, 의미 없는 색, 각 항목에 직접 이름을 붙일 수 있는데도 범례를 따로 두기, 같은 기준을 쓰지 않거나 길이가 모두 같아 차이를 알 수 없는 막대. |
| 반복되는 배치 | 모든 그래프와 계산기를 어두운 둥근 상자로 감싸기, 서로 다른 내용을 늘 같은 모양으로 배치하기. |

장식을 빼고 난 뒤에도 가장 중요한 내용은 눈에 띄어야 한다. 크기와 위치, 정렬로 읽는 순서를 분명히 만든다.

CSS와 폰트는 `scripts/build.sh`가 파일로 이어 붙인다. 에이전트는 폰트 데이터가 들어 있는 `assets/font.css`와 큰 파일인 `assets/brand.css`를 통째로 읽지 않는다. 클래스 설명으로 해결되지 않는 문제는 `rg`로 관련 CSS 규칙만 찾아 확인한다. `assets/page.css`는 우리가 추가한 스타일을 고치거나 그 동작을 확인할 때 필요한 부분만 읽는다.

이 페이지에만 필요한 CSS는 본문 파일의 `<style>`에 둔다. 제공된 CSS 클래스와 변수의 값을 임의로 덮어쓰지 않는다.

## 완성된 화면 확인하기

새 페이지는 아래 항목을 확인한다. 기존 페이지의 작은 수정은 바뀐 부분과 그 영향을 받는 곳을 중심으로 본다. `preview.sh`로 만든 라이트·다크·모바일 캡처에서 첫 화면과 페이지 하단을 살핀다.

- 첫 화면과 제목, 표·그림의 설명만으로 중요한 내용을 이해할 수 있는가. 자료의 사실과 숫자, 단위, 기간, 조건이 그대로 남아 있는가.
- 가장 중요한 내용이 먼저 보이는가. 이유 없이 빈 칸이 생겼거나 같은 내용이 반복되지는 않는가. 빈 칸이 생기면 HTML 요소를 설명대로 넣었는지도 확인한다.
- 본문과 표, 이미지가 잘리지 않고 읽히는가. 비교하는 값의 글자 크기와 굵기, 정렬이 같은가. 표가 사용할 수 있는 너비를 충분히 쓰는가. 한국어 제목이 어절 중간에서 끊기지 않는가.
- 라이트·다크 모드에서 중요한 내용이 똑같이 잘 보이는가. 모바일에서 페이지 전체를 옆으로 밀어야 읽을 수 있는 부분이 생기지 않았는가.
- `h1`이 하나이고 제목 단계가 순서에 맞는가. 표의 `caption`과 `scope`, 이미지 대체 텍스트, 어디로 가는지 알 수 있는 링크 문구가 있는가.
- 계산기, 필터, 펼치기 버튼이 있으면 직접 써 본다. 대표 입력과 결과, 최솟값·최댓값이나 잘못된 입력에 대한 처리, 키보드 조작을 해당 기능에 맞게 확인한다. 이런 기능이 없는 페이지에는 동작 검사를 추가하지 않는다.

문제가 보이면 고치고 바뀐 부분을 다시 확인한다. 위 항목을 충족하면 취향만을 위한 반복 수정은 멈춘다. 도구 문제로 확인하지 못한 부분은 확인했다고 말하지 않고 사용자에게 짧게 알린다.

사용자가 자세한 검토 결과를 요청하지 않았다면, 마지막 답변에는 고친 내용과 아직 확인하지 못한 부분만 짧게 적는다.
