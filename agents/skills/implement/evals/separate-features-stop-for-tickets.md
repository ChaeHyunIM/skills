# 기능 하나는 DB부터 UI까지 이어서 하고, 따로 쓰는 기능이 섞이면 멈춘다

## 상황 A — 기능 하나

- 사용자가 `implement 영수증 미션 기능 추가. 제출 화면, 어드민 검수, 포인트 지급까지` 를 호출했다.
- DB 스키마·마이그레이션, API, 앱 제출 화면, 어드민 검수 화면이 모두 필요하다. 제출·검수·지급은 하나의 흐름이라 따로 쓸 수 없다.

## 기대 행동 A

1. 기능 하나로 보고 완료 조건 초안을 DB부터 화면까지 한 번에 보여 주고 승인받는다.
2. 승인 뒤 같은 worktree와 PR 하나에서 스키마부터 화면까지 구현하고 검증한다.

## 하면 안 되는 행동 A

- 스키마·API·화면이 모두 필요하다는 이유로 멈추고 `to-tickets` 를 제안한다.
- 스키마만 먼저 PR 로 올리고 나머지를 다음 작업으로 미룬다.

## 상황 B — 따로 쓰는 기능이 섞임

- 사용자가 `implement 영수증 미션 추가하고, 마이페이지 프로필 사진 변경도 넣어 줘` 를 호출했다.
- 두 기능은 서로 없어도 각각 쓸 수 있다.

## 기대 행동 B

1. 따로 쓸 수 있는 기능 두 개라는 근거를 한 줄로 보여 준다.
2. 하나씩 `implement` 로 진행하거나 `to-tickets` 로 나누자고 제안하고 멈춘다.

## 하면 안 되는 행동 B

- 두 기능을 PR 하나에 섞어 구현한다.
- `to-tickets` 절차 없이 트래커에 티켓을 직접 만든다.

## 근거

설계 의도에서 만든 시나리오다. 아직 실사례는 없다. 기능 하나를 레이어로 쪼개지 않는다는 결정(2026-10-29)이 이 스킬에서 지켜지는지 본다.
