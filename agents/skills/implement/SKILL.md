# implement

티켓의 구현과 실제 동작·코드 품질 검증을 마치고 PR을 준비한다. 확인한 결과와 남은 항목을 PR에 적는다. 필요한 검증이 모두 끝났으면 사람이 병합을 판단할 수 있다.

시작할 때 [공유 규칙](../agent-loop/CONTRACT.md)을 읽는다. 티켓 처리는 [트래커 규칙](../agent-loop/references/tracker.md), 작업 폴더와 커밋은 [작업 환경](../agent-loop/references/workspace.md), 검증은 [검증과 기록 방법](../agent-loop/references/verification.md)을 따른다.

## 구현할 티켓과 작업 폴더 확인

- `implement <N> [--base <branch>]`는 지정한 티켓을 구현한다. 나머지 인자는 이번 작업에 대한 추가 지시다.
- 티켓을 지정하지 않았으면 [후보 고르기](references/candidates.md)에 따라 목록을 보여 주고 선택받는다. 이번 세션에서 이미 지정한 티켓을 다시 묻지 않는다.
- 이슈와 완료 조건, 기존 PR과 브랜치를 읽는다. 처음 구현하는 티켓인지, 기존 작업을 이어가는지 확인한다. 기존 작업은 같은 PR과 worktree에서 이어간다. 다른 구현이나 리뷰가 진행 중이면 동시에 브랜치를 고치지 않는다.
- 처음 구현할 때는 선행 티켓이 실제로 끝났고 연결된 PR도 머지됐는지 확인한다. 아직 열려 있으면 시작하지 않는다. 기존 작업을 이어갈 때도 새 선행 작업이 추가됐는지 확인한다.
- 완료 조건이 모호하면 [완료 조건 작성 기준](../agent-loop/references/ticket-criteria.md)으로 뜻을 확인한다. 제품 결정이 필요한 부분은 남겨 두고, 영향받지 않는 조사와 준비는 계속한다.
- 상태를 `in-progress`로 바꾼다. 새 작업의 base는 사용자가 지정한 브랜치나 메인 체크아웃의 현재 로컬 브랜치로 정한다. `main`이라고 가정하지 않는다.

```bash
bash ~/.agents/skills/implement/scripts/prepare-worktree.sh <N> <ascii-slug> [<base>]
```

기존 작업을 이어갈 때는 base를 생략한다. 로컬 변경이나 아직 원격에 올리지 않은 커밋이 있으면 보존하고 어느 작업에서 만든 것인지 확인한다. 기존 PR의 worktree를 원격 브랜치에 맞출 때는 [sync-worktree.sh](../agent-loop/scripts/sync-worktree.sh)를 사용한다.

## 구현하고 검증하기

- 이슈의 목표와 완료 조건, 프로젝트 지침을 따른다. Figma 링크가 있는 UI는 해당 스킬과 도구로 디자인을 읽고 배치와 스타일을 맞춘다. 디자인과 승인된 정책이 충돌하면 그 부분을 확인받는다.
- 필요한 테스트, API 요청, 브라우저·시뮬레이터·기기 확인을 실제로 수행한다. 구현 중이라는 이유로 UI 확인을 금지하거나 다음 `verify` 호출로 미루지 않는다.
- [code-quality](../code-quality/SKILL.md)로 변경에 맞는 전문 스킬을 읽고 코드 품질을 확인한다. 작업 범위 안에서 발견한 문제는 이번 구현에서 고친다.
- 진입 방법·준비 상태·함정을 찾느라 헤맸다면 프로젝트 검증 스킬의 방식대로 기능 메모에 남긴다. 문구나 좌표로만 잡힌 핵심 요소에는 안정적인 식별자를 붙인다. 둘 다 이번 PR에 포함한다. 프로젝트 검증 스킬이 없으면 새로 만들지 않는다.
- 화면이나 사용자 흐름을 추가·변경했다면 [필수 기록물](../verify/references/routes.md)을 남기고 사람이 열어볼 수 있게 전달해야 검증이 끝난다. 유효한 기존 결과와 기록물은 재사용한다.
- 캡처·녹화나 반복 실행 방법은 [web](../verify/references/web-playwright.md)·[앱](../verify/references/app-argent.md), 기록물 점검은 [검증 근거 확인](../verify/references/quality-gates.md)을 따른다.
- 작업 범위 안에서 발견한 구현 오류는 고치고 관련 검사를 다시 한다. 회귀 테스트는 같은 문제가 다시 생길 위험과 반복 사용할 가치를 보고 추가한다. 타입 체크 통과를 실제 동작의 증거로 쓰지 않는다.
- 확인할 수 없는 조건은 실제 환경 문제나 권한 부족을 확인한 뒤 미검증으로 남긴다. “설치 여부 미확정”처럼 확인하지 않은 추측을 이유로 쓰지 않는다. 다른 조건은 계속 확인한다.

## 최종 코드를 확인하고 PR 준비하기

1. origin을 fetch하고 로컬 base와 원격 base를 비교한다. 로컬에만 있는 커밋이 있으면 사용자의 base를 대신 push하지 않고 알린다. 원격 base에 새 커밋이 있으면 작업 브랜치에 merge하고 관련 검사를 다시 한다. 충돌을 임의로 해결하지 않고 기록한다.
2. 작업 환경 문서의 `comment-cleaner` → 필요한 검사 → `commit` 순서를 따른다. 새 테스트도 커밋에 포함한다. 최종 커밋에서 검증하거나, 앞서 실행한 코드와 입력이 최종 커밋에서도 같음을 확인한다. 검사 후 코드가 바뀌었으면 기존 결과를 그대로 쓸 수 있는지 다시 판단한다.
3. 작업 브랜치를 push한다. PR head가 검증한 커밋과 같고 worktree에 커밋하지 않은 변경이 없는지 확인한다. 결과는 공통 검증 문서의 형식으로 적는다. 게시 방법이 필요하면 [PR에 검증 결과 적기](../verify/references/publishing.md)를 읽는다.
4. 새 작업은 draft가 아닌 PR을 연다. 본문은 [PR 본문 양식](../agent-loop/references/pr-body.md)을 따른다. 기존 PR은 최신 본문에서 에이전트가 쓴 섹션과 검증 결과만 고치고, 다른 사람이 쓴 글은 보존한다.
5. 게시한 본문, PR head, 티켓 상태를 다시 확인한다. 필요한 검증이 모두 끝났으면 작업을 마친다. 남은 검증이 있을 때만 그 항목과 `verify <N>`으로 이어갈 수 있음을 안내한다.

머지는 이 스킬에서 시작하지 않는다. 진행 상황을 보여 주려고 구현 도중 PR을 먼저 열지 않는다.

## 결과와 남은 일 보고하기

- 구현과 검증 결과가 준비됐으면 `awaiting-review`로 바꾼다. 환경 문제로 확인하지 못한 조건은 PR과 채팅에 적는다.
- 해결하지 못한 구현 오류, 제품 결정, base 충돌이 있으면 `blocked`로 남긴다. 이유와 다시 시작하는 방법을 적는다. 열린 PR에 base 충돌만 남았다면 `land`로 이어갈 수 있다. PR이 아직 없으면 구현을 이어가 PR부터 준비한다.
- 팀에 결정을 요청할 코멘트는 초안을 승인받는다. 승인을 기다리는 동안 다른 작업은 마친다.

마지막 보고에는 PR 링크, 실제 검증 결과와 기록물, 남은 항목과 필요한 결정을 적는다. 이슈의 완료 조건 체크박스는 바꾸지 않는다.
