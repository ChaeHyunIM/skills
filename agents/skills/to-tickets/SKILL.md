# to-tickets

승인된 목표를 구현하고 검증할 수 있는 티켓으로 만든다. 티켓 하나만 만들 때도 이 스킬을 사용한다. 트래커의 상위 티켓과 선행 작업 기능으로 관계를 연결하고, 필요한 속성도 확인한다.

시작할 때 [공유 규칙](../agent-loop/CONTRACT.md)과 [트래커 규칙](../agent-loop/references/tracker.md)을 읽는다. 완료 조건은 [작성 기준](../agent-loop/references/ticket-criteria.md), 여러 티켓으로 나눌 때는 [작업을 나누는 기준](references/slicing-rules.md)을 따른다.

## 티켓으로 나눌 작업 정하기

- 대화, 스펙, 상위 이슈에서 승인된 목표를 확인한다. 현재 코드와 용어집, 관련 설계 결정 문서(ADR)는 동작과 제약, 선행 작업을 파악할 만큼 읽는다. 관련 없는 문서까지 모두 읽을 필요는 없다.
- 별도 디자인이 있는 UI는 Figma에서 확인하고 링크를 남긴다. 디자인을 글로 다시 묘사하지 않는다. 필요한 디자인 링크가 없으면 그 UI를 어떻게 할지 확인하고, 나머지 작업은 계속한다.
- 디자인에 빠진 상태, 문구, 정렬 순서, 한도를 확인한다. 코드와 디자인이 다른 부분도 살핀다. 기존 코드나 문서에 답이 있으면 출처를 적고, 새 제품 정책이 필요한 부분은 결정이 남았다고 표시한다.
- 승인된 선행 작업이 머지되면 각 티켓만으로 하나의 결과를 완성하고 검증할 수 있게 나눈다. 완료 조건을 모두 만족하면 목표도 달성되는지, 합의하지 않은 작업이 완료 조건에 끼어 있지는 않은지 확인한다.
- 머지한 뒤에만 검증할 수 있는 항목은 승인받은 후속 티켓으로 남긴다. 트래커의 선행 작업 기능으로 구현 티켓과 연결해 확인할 일이 빠지지 않게 한다.

## 게시할 내용 보여 주고 확인받기

실제로 올릴 제목, 목표, 완료 조건을 보여 준다. 상위 티켓과 먼저 끝나야 할 작업, 그 이유도 함께 적는다. 이번 티켓에 포함할 일과 제외할 일을 분명히 한다. 크기나 우선순위 같은 속성은 [속성 지정 기준](references/attributes.md)에 따라 근거가 있는 값만 제안한다. 사용자가 이미 지정하거나 승인한 내용을 다시 묻지 않는다.

- 제품 정책을 새로 정해야 하면 어떤 상황인지, 선택지마다 사용자에게 무엇이 달라지는지, 추천과 이유를 짧게 설명한다. 단순한 구현 방식까지 모두 정책 질문으로 만들지 않는다.
- 상위 티켓이 있으면 결정 기록을 그곳에 모은다. 없으면 승인된 티켓 중 관련 있는 곳에 남기는 방안을 제안한다. 티켓이 아직 없다는 이유로 기록할 위치만 반복해서 묻지 않는다.
- 게시할 내용과 필요한 정책 결정을 승인받은 뒤 티켓과 결정 코멘트를 작성한다. 팀이 읽고 결정해야 하는 코멘트는 전체 초안을 보여 주고 승인받는다. 채팅에서 정한 정책도 트래커에 출처와 함께 남긴다.
- 정책 결정이 남은 티켓은 `ready`로 만들지 않는다. 그 결정에 영향받지 않는 작업은 계속한다. 결정 코멘트를 올리지 못했으면 초안을 보존하고 아직 남기지 못한 기록을 보고한다.

## 티켓 만들고 확인하기

[티켓 본문 형식](references/ticket-body.md)을 사용한다. 제목은 프로젝트의 제품 접두어와 한국어 제목 규칙을 따르고, 본문은 `korean-output` 스킬을 적용한다. 어떤 파일이나 함수를 고칠지에 대한 구현 계획은 PR에 적는다.

1. 선행 티켓부터 만든다. 승인된 속성과 상위 티켓, `blocked-by` 관계를 지정하고 스펙이 확정된 티켓은 `ready`로 둔다. 선행 티켓이 아직 열려 있어도 `ready`다.
2. 만든 티켓과 관계를 다시 읽는다. 완료 조건 원문, 상위 티켓, 선행 작업, 속성이 승인받은 내용과 같은지 확인한다. 빠진 것은 바로 보완하되 새 정책이나 의존 관계를 추측해서 넣지 않는다.
3. 본문에 선행 작업 목록을 중복해서 적지 않았는지 확인한다. 의존하는 이유를 설명하는 한 문장은 남겨도 된다. 새 완료 조건 체크박스는 빈칸이다.
4. 결정 기록이 있으면 승인된 답과 출처가 트래커에 남았는지 확인한다. 상위 티켓의 본문이나 상태를 임의로 바꾸거나 닫지 않는다.

마지막에는 티켓 링크, 진행 순서, 보류한 작업과 필요한 결정을 보고한다. 일부 작업이 실패해도 이미 만든 티켓을 다시 만들지 않는다. 실제 상태를 확인하고 빠진 부분만 보완한다.
