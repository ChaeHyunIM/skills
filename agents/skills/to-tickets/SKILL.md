# to-tickets

새 티켓은 단건이어도 이 스킬을 통한다. 승인된 목표를 구현·검증 가능한 티켓으로 만들고 네이티브 부모·blocked-by 관계와 속성을 확인한다.

시작할 때 `~/.agents/skills/agent-loop/CONTRACT.md`와 공통 `references/tracker.md`를 읽는다. 완료 조건을 쓸 때는 공통 `references/ticket-criteria.md`, 여러 작업을 나눌 때는 [references/slicing-rules.md](references/slicing-rules.md)를 읽는다.

## 맥락과 분할

- 대화·스펙·부모 이슈의 승인된 목표로 시작한다. 코드·용어집·관련 ADR은 해당 영역의 현재 동작·제약·의존을 확인할 만큼 읽는다. 티켓 작성 때문에 관계없는 문서 전체를 요구하지 않는다.
- 별도 디자인이 있는 UI면 Figma 노드를 읽고 링크를 남긴다. 디자인을 산문으로 복제하지 않는다. 링크가 필요한데 없으면 해당 UI의 결정을 확인하고 독립적인 범위는 계속한다.
- 디자인에 없는 상태·카피·정렬·한도와 코드·디자인의 충돌을 확인한다. 코드·문서에 답이 있으면 출처를 기록하고, 제품이 무엇을 할지 새로 정해야 하면 미결 정책으로 남긴다.
- 티켓마다 승인된 선행 작업이 머지된 상태에서 완결된 결과를 낼 수 있게 나눈다. 목표와 완료 조건을 양방향으로 대조한다. 머지 후에만 검증 가능한 조건은 승인된 후속 티켓과 네이티브 엣지로 범위를 보존한다.

## 검토와 승인

실제 게시할 제목·목표·완료 조건·선행 티켓과 이유·부모·범위 경계를 제시한다. 트래커 속성을 지정할 때는 [references/attributes.md](references/attributes.md)로 근거 있는 값만 제안한다. 이미 사용자가 지정한 값과 승인한 내용을 다시 묻지 않는다.

- 새 제품 정책은 걸리는 상황, 선택지의 사용자 영향, 추천과 근거를 짧게 제시한다. 기술 구현 선택을 모두 정책 질문으로 확대하지 않는다.
- 부모가 있으면 결정 기록을 부모에 모은다. 부모가 없으면 승인된 티켓 중 관련 있는 곳에 남기는 방안을 제안한다. 티켓이 아직 없다는 이유로 기록할 위치 질문만 반복하지 않는다.
- 게시·정책 결정을 승인받은 뒤 티켓과 필요한 결정 코멘트를 작성한다. 팀이 읽고 결정해야 하는 글은 전문 초안을 승인받는다. 채팅에서 정한 정책도 트래커에 출처로 남긴다.
- 미결 정책에 걸린 티켓은 `ready`로 발행하지 않는다. 영향받지 않는 슬라이스는 진행한다. 결정 코멘트가 게시될 수 없으면 초안을 보존하고 어떤 기록이 남았는지 보고한다.

## 발행과 확인

[references/ticket-body.md](references/ticket-body.md)의 본문 형식을 사용한다. 한국어 제목은 프로젝트의 제품 접두어 규칙을 따르고, 본문은 `korean-output`을 적용한다. 구현 파일·함수 배정은 PR에 둔다.

1. 선행 티켓부터 발행하고 `ready`, 승인된 속성, 필요한 부모·blocked-by를 건다. 블로커가 열려 있어도 스펙이 확정됐으면 ready다.
2. 게시한 티켓·관계를 읽어 승인된 조건 원문·부모·엣지·속성이 맞는지 확인한다. 누락은 바로 고치되 새 정책·의존은 추측하지 않는다.
3. 본문에 별도 blocker 목록이 없는지 확인한다. 의존 이유 한 문장은 허용한다. 새 체크박스는 빈칸이다.
4. 결정 기록이 있으면 승인된 답과 출처가 트래커에 남았는지 확인한다. 부모 본문·상태를 임의로 고치거나 닫지 않는다.

티켓 링크와 의존 순서, 보류된 범위·결정만 보고한다. 일부 외부 작업이 실패해도 성공한 발행을 다시 만들지 않고 실제 상태를 읽어 누락만 복구한다.
