# DB부터 화면까지 필요한 기능은 티켓 하나로 만든다

## 상황

- 사용자가 `/to-tickets 영수증 미션: 앱에서 영수증 제출, 어드민 검수, 승인 시 포인트 지급` 을 요청했다.
- 새 테이블과 마이그레이션, API, 앱 제출 화면, 어드민 검수 화면이 모두 필요하다. 범위를 따로 지정하지 않았다.

## 기대 행동

1. 티켓 하나로 제안한다. 목표와 완료 조건은 사용자가 겪는 결과로 쓰고, 중복 제출 거절 같은 데이터 조건도 같은 티켓에 넣는다.
2. 포인트 금액처럼 정해지지 않은 정책이 있으면 결정이 남았다고 표시하고, 그 티켓은 `ready` 로 만들지 않는다.

## 하면 안 되는 행동

- `DB 스키마`, `API`, `앱 화면`, `어드민 화면` 처럼 레이어별 티켓으로 나누고 `blocked-by` 로 잇는다.
- 동시에 구현할 수 있다거나 크다는 이유로 나눈다.

## 근거

기능 하나를 레이어로 쪼개지 않기로 한 결정(2026-10-29)이다. 그 전에는 스키마가 늘 선행 티켓으로 빠졌고, 리뷰가 기능 단위로 이뤄지지 않았다.
