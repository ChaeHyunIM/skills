# 작업을 여러 티켓으로 나누는 기준

여러 티켓을 만들 때 읽는다. 규칙이 생긴 배경이 궁금할 때만 [이전 확인 기록](../../agent-loop/references/evidence.md)을 읽는다.

## 티켓마다 완성할 결과 정하기

- 기본 단위는 사용자에게 보이는 동작이다. API, 관리자 화면, 앱 화면을 함께 고쳐야 하나의 동작이 완성된다면 같은 티켓으로 묶는다. 백엔드, 스키마, 인프라는 개발자가 확인할 수 있는 완성된 결과를 기준으로 나눈다.
- 각 티켓은 승인된 선행 티켓이 머지된 상태에서 단독으로 머지할 수 있어야 한다. 제품이 정상 동작하고 해당 결과를 검증할 수 있어야 한다는 뜻이다. 모든 후속 티켓이 처음의 base에서 바로 컴파일돼야 한다는 뜻은 아니다.
- B가 A에서 새로 만드는 스키마, API, 타입을 사용한다면 A를 선행 작업으로 연결하고 A가 머지된 뒤 B를 구현한다. 이 관계만으로 두 티켓을 합치지는 않는다.
- A와 B가 서로 없으면 동작하지 않거나, 하나만 머지하면 약속한 기능을 절반밖에 쓸 수 없다면 함께 묶는다. 또는 중간 단계에서도 정상 동작하도록 순서와 범위를 다시 나눈다.

## 동시에 할 수 있는 작업 구분하기

- 같은 모듈이나 화면을 고친다면 충돌할 가능성을 살핀다. 수정할 부분이 분리되고 각각 결과를 완성할 수 있으면 반드시 같은 티켓으로 묶을 필요는 없다.
- 선행 작업이 없는 티켓은 동시에 구현해도 API 등의 약속이나 상태 변경이 충돌하지 않는지 확인한다. 실제로 먼저 끝나야 하는 작업은 트래커의 관계 기능으로 연결한다. 같은 파일을 고친다는 이유만으로 선행 작업을 만들지는 않는다.
- 사용하는 화면, 심볼, API는 자기 티켓의 변경이나 이미 머지된 선행 작업에 있어야 한다. 나중 티켓에서 만들 예정인 기능을 먼저 참조하지 않는다.
- 새 화면을 만드는 티켓에서 그 화면으로 들어가는 버튼이나 링크도 연결한다. 앞 티켓에서 아직 없는 화면으로 이동하는 버튼을 활성화하지 않는다. 기존 버튼을 잠시 비활성화하면서 서비스 중인 기능이 사라진다면 프로젝트의 삭제·정책 확인 규칙을 먼저 따른다.

## 마이그레이션과 여러 곳에 걸친 리팩터링

- 동시에 진행할 여러 티켓이 스키마를 바꾸면 공통 스키마 작업을 선행 티켓으로 모으고 마이그레이션 journal 순서를 맞춘다. 각 기능 티켓에 그 선행 작업을 연결한다. 마이그레이션 생성과 적용은 프로젝트 지침을 따른다.
- 이름을 여러 곳에서 바꾸거나 공유 타입을 변경할 때는 새 형식을 추가하고(expand), 사용하는 코드를 옮긴 뒤(migrate), 옛 형식을 제거한다(contract). 옮기는 작업은 기존 코드와 함께 동작하는 단위로 나누고, 옛 형식은 모든 사용처를 옮긴 뒤 제거한다.
- 그래도 티켓 하나씩 정상 동작하는 상태로 머지할 수 없다면 합치거나 사용자와 통합 브랜치 사용을 정한다. 통합 브랜치를 쓰기로 했다는 이유로 일반 `implement`의 브랜치 규칙까지 임의로 바꾸지 않는다.
