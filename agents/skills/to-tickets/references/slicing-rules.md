# 티켓 범위 정하기

목표를 티켓으로 만들 때 읽는다. 규칙이 생긴 배경이 궁금할 때만 [이전 확인 기록](../../agent-loop/references/evidence.md)을 읽는다.

## 기본: 기능 하나에 티켓 하나

- 사용자가 쓸 수 있는 기능 하나를 티켓 하나로 만든다. 스키마·마이그레이션, API, 관리자 화면, 앱 화면이 모두 필요하면 전부 같은 티켓에 담는다. 리뷰어가 기능 하나를 처음부터 끝까지 한 PR에서 판단할 수 있게 하기 위해서다.
- 레이어, 크기, 동시에 구현할 수 있는지는 나눌 이유가 아니다. 한 에이전트가 기능 전체를 이어서 구현한다.
- 새 화면으로 들어가는 버튼이나 링크도 그 화면을 만드는 티켓에 담는다.

## 사용자가 범위를 정했을 때

사용자가 "스키마만 먼저"처럼 범위를 직접 정하면 그 범위로 티켓을 만든다. 그 티켓만 머지했을 때 제품이 어중간해지면 한 번 짚는다. 예를 들어 동작하지 않는 진입 버튼이 생기거나, 서비스 중인 기능이 사라지는 경우다. 그래도 사용자가 정한 범위를 따른다. 남은 부분을 이어받을 티켓이 있으면 선행 작업으로 연결한다.

## 나눌 수밖에 없을 때

에이전트가 스스로 나누는 경우는 아래뿐이다. 나눌 때는 이유를 한 줄로 보여 주고 승인받는다.

- 사용자가 따로 쓸 수 있는 기능이 둘 이상이다.
- 배포를 사이에 둬야 하는 단계가 있다. 이름 변경이나 공유 타입 변경은 새 형식을 추가하고(expand) 사용처를 옮긴 뒤, 배포 후에 옛 형식을 제거한다(contract). contract는 옛 코드가 새 스키마를 보는 구간이 끝난 뒤의 별도 티켓이다.
- 머지한 뒤에만 확인할 수 있는 항목이 있다. [완료 조건 작성 기준](../../agent-loop/references/ticket-criteria.md)대로 후속 티켓으로 남긴다.

나눈 티켓은 각각 단독으로 머지해도 제품이 정상 동작해야 한다. 뒤 티켓이 앞 티켓의 스키마·API·화면을 쓰면 앞 티켓을 선행 작업으로 연결하고, 아직 없는 것을 먼저 참조하지 않는다.

## 서로 다른 기능 티켓이 겹칠 때

- 같은 시기에 진행할 기능 티켓들이 같은 테이블이나 API 약속을 바꾸면 충돌을 살핀다. 실제로 먼저 끝나야 하는 쪽만 선행 작업으로 연결한다. 같은 파일을 고친다는 이유만으로 연결하지 않는다.
- 마이그레이션 생성과 적용, journal 순서는 프로젝트 지침을 따른다.
