# 티켓 본문 형식

아래 설명을 실제 작업 내용으로 바꿔 쓴다. 필요한 섹션만 남기고, 사용자와 팀이 이 작업으로 무엇이 달라지는지 알 수 있게 적는다.

```markdown
## 목표

이 작업이 끝나면 무엇이 달라지는지 적는다. 사용자에게 보이는 기능이라면 무엇을 할 수 있게 되는지 설명한다.
여러 화면이나 API가 함께 바뀌더라도 완성되는 동작을 기준으로 쓴다.
합의한 작업 범위와 맞닿는 다른 일이 있으면 이번에 어디까지 하는지 한 문장으로 적는다.

## 제공할 동작

사용자나 시스템이 할 수 있어야 하는 일을 적는다. 주요 동작과 필요한 예외 상황을 설명한다.
어떤 파일, 함수, 컴포넌트를 고칠지는 구현자가 판단한다.

## 정책과 제약

구현 방식과 관계없이 지켜야 하는 제품 규칙이나 외부 API 등의 약속을 적는다.
규칙마다 항목을 나누고 코드, 문서, 트래커 코멘트 등 정해진 근거의 링크를 붙인다.
별도 규칙이 없으면 이 섹션은 생략한다.

## 디자인·참고

디자인이나 참고 문서가 있을 때만 적는다.

- **Figma 디자인**: 해당 노드의 링크를 남긴다. 구현할 때 MCP로 최신 디자인을 읽고 화면 구성과 스타일을 따른다.
  디자인의 동작이나 정책이 완료 조건과 충돌하면 먼저 결정받는다. 스크린샷을 붙이거나 디자인을 글로 다시 묘사하지 않는다.
- **디자인에 없는 내용**: 로딩·빈 화면·오류 상태, 조작 중 생길 수 있는 예외, 데이터 규칙, 빠진 문구를 적는다.
  항목마다 정한 답과 그 근거가 되는 코드·문서·사용자 결정을 함께 남긴다.

## 완료 조건

- [ ] 합의한 목표와 정책을 충족했는지 직접 확인할 수 있는 결과를 적는다.

결과는 반드시 적고, 전제나 행동은 뜻을 분명히 하는 데 필요할 때만 덧붙인다.
사용자에게 보이는 기능은 사용자가 겪는 결과로, 백엔드나 스키마 작업은 개발자가 확인할 결과로 쓴다.
공통 작성 기준의 예시를 따르고, 타입 체크나 수정할 파일 목록으로 대신하지 않는다.
```
