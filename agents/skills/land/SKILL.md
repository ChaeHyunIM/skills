# land

이번 실행에서 사용자가 지정한 PR을 준비하고 검사한 뒤 머지한다. 요청대로 병합할 수 있으면 호출 자체를 승인으로 보고 진행한다. 요청에 없던 변경이나 남은 검증이 있으면 준비한 결과를 보여 주고 그 부분만 확인받는다.

시작할 때 [공유 규칙](../agent-loop/CONTRACT.md)을 읽는다. 티켓과 상태는 [트래커 규칙](../agent-loop/references/tracker.md), 작업 폴더와 커밋은 [작업 환경](../agent-loop/references/workspace.md), 검증 결과와 체크박스는 [병합 전 완료 조건 확인](../agent-loop/references/landing-criteria.md)을 따른다.

## 병합할 PR 고르기

- `land <N...>`은 지정한 순서대로 처리한다. 티켓 번호가 없으면 `awaiting-review`인 후보를 모아 선택받는다. 과거 실행에서 받은 지정을 새로운 머지 승인으로 사용하지 않는다.
- `blocked`라도 최신 기록에서 base 충돌만 남았다고 확인되면 사용자가 직접 지정해 진행할 수 있다. 정책 결정이나 구현 오류도 남았거나 이유가 모호하면 먼저 해결하도록 남긴다.
- 실제 구현이 진행 중인 `in-progress`는 처리하지 않는다. 라벨만 오래 남았다면 실행이 끝났는지와 작업 기록을 확인한 뒤 상태를 바로잡는다. 별도 리뷰가 진행 중이라면 대상 브랜치를 바꾸거나 병합하지 않는다.
- PR 본문의 티켓 연결 정보로 PR, 티켓, 브랜치가 맞는지 확인한다. 최신 완료 조건과 PR 검증 결과, 해당 PR에 남은 리뷰 의견을 함께 읽는다. 필요한 검증이 끝났으면 별도 `verify` 실행을 요구하지 않는다.

## 병합할 코드 준비하기

1. 실제 worktree와 브랜치를 확인한다. 없으면 [prepare-worktree.sh](../implement/scripts/prepare-worktree.sh)로 기존 브랜치의 worktree를 복구한다.
2. [sync-worktree.sh](../agent-loop/scripts/sync-worktree.sh)에 worktree와 브랜치를 전달해 원격의 최신 커밋을 가져온다. 로컬 변경과 원격에 올리지 않은 커밋이 없을 때만 fast-forward한다. 실패하면 기존 작업을 보존하고 해당 PR은 남긴다.
3. PR의 현재 base를 다시 읽고 fetch한 base를 작업 브랜치에 merge한다. 충돌은 [충돌 해결 기준](references/conflicts.md)을 따른다. 사람이 정책이나 기능을 선택해야 하는 충돌이면 merge를 중단하고 그 PR만 `blocked`로 남긴다.
4. 합쳐진 코드에 필요한 타입 체크를 한다. 같은 코드와 입력에서 통과한 결과는 재사용한다. 요청 범위 밖의 동작을 바꾸지 않는다. 충돌을 해결하거나 코드를 수정했으면 공통 커밋 절차를 따르고 작업 브랜치를 push한다.
5. 최종 PR head, base SHA, 최신 완료 조건을 확인하고 [verified-head.sh](../verify/scripts/verified-head.sh)를 실행한다. base 반영이나 충돌 해결로 커밋이 바뀌었으면 기존 검증 기록은 `stale`이다. 기능을 검증했다고 쓰거나 검증 기록을 직접 고치지 않는다.

원격 변경을 반영하려고 `reset --hard`, 자동 stash, force-push를 사용하지 않는다.

## 남은 사항 확인하고 병합하기

병합 순서와 PR, base와 head, 충돌을 어떻게 해결했는지, 검증 결과와 남은 조건을 짧게 보여 준다. 아직 승인받지 않은 예외만 모아 묻는다. `implement`가 모든 조건을 확인했고 최종 코드에도 그 결과가 유효하면 `verify`를 요구하지 않는다.

- 사용자가 대상을 지정했고 예상 밖 변경이나 남은 조건이 없으면 추가 질문 없이 진행한다.
- 검증 기록이 `stale`·`missing`이거나 미충족·미검증 조건이 있는데도 머지하려면, 어떤 확인이 빠졌는지 보여 주고 승인받는다. 다시 검증하려면 `implement` 또는 `verify`로 진행할 수 있다.
- 앞 PR을 머지하면 뒤 PR의 base가 바뀌는 경우, 그 영향과 다시 확인해야 할 부분을 미리 설명한다. 이 상황까지 승인받지 않았다면 이전 검증 결과를 새 코드에서도 통과한 것으로 처리하지 않는다.
- 각 PR을 머지하기 직전에 원격 head와 base, 이슈의 완료 조건을 다시 읽는다. base가 움직였으면 다시 반영하고 검사한 뒤 검증 결과를 재평가한다. 승인받은 내용에 없는 변경은 그 PR만 보류하고, 영향받지 않는 PR은 계속 처리한다.
- 완료 조건 문서에 따라 이슈의 체크박스를 바꾸고 저장 결과를 확인한다. `current` 기록에서 근거로 확인된 충족 항목만 체크한다. 저장하거나 확인하지 못하면 그 PR을 머지하지 않는다.
- `gh pr merge <PR> --rebase --match-head-commit <final-head>`로 병합한다. 머지하는 순간에도 PR head가 확인한 커밋과 같을 때만 진행하도록 하는 옵션이다. 지원하지 않는 도구라면 같은 조건을 보장하는 다른 도구를 사용한다. 그런 도구가 없으면 해당 머지를 보류한다. head가 달라지면 다시 확인한다.

## 결과 확인과 보고

실제로 머지됐고 트래커도 완료 상태인지 확인한다. `Fixes` 연동으로 상태가 바뀌지 않았으면 직접 완료 처리한다. 미완료 항목이 남은 채 머지하도록 승인받았다면 병합 전 완료 조건 문서에 따라 PR과 이슈에 기록한다. 기록만 실패했으면 빠진 기록을 보완하고 머지를 다시 실행하지 않는다.

보고에는 남은 미충족·미검증 항목과 보류·실패 내용을 먼저 적고, 머지 결과와 기록 링크를 이어서 적는다. worktree는 남겨 두고 세션이 끝난 뒤 `tidy-merged`로 정리한다.
