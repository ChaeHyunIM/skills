# PR 본문

PR 본문은 사람이 읽는다. 리뷰어가 병합해도 되는지, 배포할 때 무엇을 조심할지, 무엇을 정해야 하는지 판단하는 데 필요한 것만 적는다.

PR 본문에 커밋이나 diff를 그대로 풀어 쓰지 않는다. 리뷰어가 왜 이렇게 바꿨는지 이해하고, 어디를 중점적으로 봐야 하는지 알 수 있게 쓴다.

여러 파일에 걸친 호출 관계나 컴포넌트 구조의 변화는 diff만으로 파악하기 어렵다. `구조 변경` 섹션에서는 바뀐 구조와 주변 맥락을 다이어그램으로 보여 준다. 개별 코드의 동작 설명은 반복하지 않는다.

## 양식

```markdown
Closes YOU-000 · base: `main`

<!-- decisions:start -->
> [!IMPORTANT]
> **정해야 할 것 N건** — 정하기 전에는 머지하지 않는다.

- [ ] <갈림길> — A: <선택지> / B: <선택지>. 추천: A, <이유 한 줄>
<!-- decisions:end -->

## 무엇이 달라지나

<사용자·운영자가 겪는 변화 1~3문장>

## 구조 변경

<변경 범위에 맞는 다이어그램 하나>

리뷰 순서: `<진입점>` → `<설계 판단이 필요한 부분>` → 나머지 단순 변경

## 리뷰 포인트

- `<파일 또는 영역>` — <먼저 봐야 하는 이유>

## 배포 영향

<마이그레이션·환경 변수·배포 순서·백필. 없으면 "없음">

되돌리기: <revert로 충분 | revert 후에도 남는 것>

## 범위 밖

- <이번 PR이 하지 않은 것과 이어받을 곳>

<!-- verify:start -->
## 완료 조건 검증
...
<!-- verify:end -->
```

섹션 이름과 순서는 바꾸지 않는다. 리뷰어가 PR마다 필요한 내용을 쉽게 찾을 수 있도록, 사람이 정해야 할 것을 맨 위에 두고 동작 변화와 구조, 리뷰 포인트와 배포 영향을 이어서 적는다.

용어는 저장소의 도메인 모델(`CONTEXT.md`)을 따른다. 새 용어를 도입했다면 `무엇이 달라지나`에서 한 줄로 설명한다.

## 섹션별 기준

**티켓 연결 줄** — 필수. `Closes`로 티켓을 연결하고 실제 base를 적는다. 티켓이 없으면 base만 적는다.

**정해야 할 것** — 있을 때만. 제품 정책·비용·사용자에게 보이는 동작처럼 에이전트가 정하지 않고 보류한 항목이다. 티켓 연결 줄 바로 아래 `decisions` 마커 안에 쓴다. `> [!IMPORTANT]` 알림으로 남은 건수를 알리고, 항목은 알림 밖에 체크박스 목록으로 적는다. 완료 조건 검증의 체크박스와 섞이지 않도록 마커 밖에는 결정 항목을 쓰지 않는다. 항목마다 선택지와 추천을 함께 적는다. 팀이 정해야 하는 항목은 프로젝트 지침에 따라 트래커 코멘트 초안도 따로 준비한다.

정해지면 해당 줄을 `- [x] <갈림길> → <고른 선택지>`로 바꾸고, 결정을 반영하는 커밋이 필요하면 그 커밋까지 올린다. 알림의 건수도 남은 수로 고치고, 모두 정해지면 알림을 `> [!NOTE]`와 `**정해진 것**`으로 바꾼다. `land`는 마커 안에 `- [ ]`가 남은 PR을 그대로 머지하지 않는다.

**무엇이 달라지나** — 필수. 코드 용어 없이, 기능을 쓰는 사람 입장에서 바뀐 동작을 쓴다. 내부 리팩터링처럼 사용자가 겪는 변화가 없으면 "동작 변화 없음"과 바뀐 이유 한 문장을 쓴다.

**구조 변경** — diff 첫 화면만으로 변경을 파악할 수 있으면 생략한다. 그 밖에는 [다이어그램 선택](#다이어그램-선택)을 따른다. 다이어그램 아래에는 리뷰 순서 한 줄만 적는다.

**리뷰 포인트** — 있을 때만. diff에서 먼저 봐야 할 곳 2~3개와 그 이유를 적는다. 변경 사항을 나열하지 않고, 주의해서 봐야 할 로직이나 검토가 필요한 설계 결정을 짚는다.

**배포 영향** — 필수. 내용이 없어도 "없음"으로 채운다. 섹션이 빠진 PR과 영향이 없는 PR을 구분하기 위해서다. 적을 것:
- 마이그레이션 파일 이름과, 사람이 직접 적용해야 한다는 사실
- 새로 필요한 환경 변수·시크릿과, 설정해야 하는 곳
- 서버와 앱처럼 배포 순서가 있으면 그 순서와 이유
- 백필이나 데이터 정리가 필요하면 대상과 실행 주체

`되돌리기`는 반드시 적는다. revert PR 하나로 원래 상태로 돌아갈 수 있으면 "revert로 충분"이라고 쓴다. 그렇지 않으면 revert 후에도 남는 영향을 적는다. 이미 적용된 마이그레이션, 백필된 데이터, 발송한 푸시·메일, 처리된 결제, 공개된 API, 이미지 변환 비용 등이 해당한다.

**범위 밖** — 있을 때만. 티켓 범위 안인데 하지 않은 것, 발견했지만 손대지 않은 문제를 적는다. 후속 티켓이 있으면 연결한다.

**완료 조건 검증** — [검증과 기록 방법](verification.md)의 형식을 따른다. 근거는 리뷰어가 한 번 읽고 믿을 수 있을 만큼만 쓴다. 재현 방법과 관찰 결과를 적고, 결과를 재사용한 논증이나 내부 식별자 나열은 줄인다.

## 다이어그램 선택

변경 전체를 보여 줄 수 있는 가장 작은 범위의 형식을 고른다. 함수·모듈·화면·파일 수준의 변경은 아래 표의 첫 네 형식으로 표현한다. 이런 변경에 시스템 다이어그램까지 그릴 필요는 없다.

| 변경 범위 | 확인할 내용 | 형식 |
|---|---|---|
| 함수 하나 안의 조건·상태 | 분기가 어떻게 바뀌었나 | 의사코드 diff |
| 한 모듈 안의 호출 흐름 | 호출 관계가 어떻게 바뀌었나 | call tree diff |
| 화면 하나 | 컴포넌트가 어디에 추가되거나 이동했나 | 컴포넌트 트리 diff |
| 파일 이동·분리 | 어떤 책임이 어느 파일로 옮겨졌나 | 파일 트리 diff |
| API·서비스·DB 경계를 넘는 한 흐름 | 요청이 어디를 거치나 | mermaid sequence |
| 새 서비스·큐·워커·엔드포인트 | 시스템 구성이 어떻게 바뀌었나 | mermaid flowchart |

작성 기준:

- 변경된 노드의 위치를 알 수 있도록 바뀌지 않은 부모·형제도 남긴다. `+` 줄만 나열하지 않는다.
- 노드 이름은 코드의 실제 식별자를 쓴다.
- 각 노드의 동작 설명은 다이어그램 아래에 덧붙이지 않는다. 필요한 설명은 코드 주석에 쓴다.
- 여러 범위에 걸친 변경은 가장 큰 범위의 다이어그램 하나로 보여 준다. 세부 변경은 `리뷰 포인트`에 해당 파일을 적는다.

call tree diff 예시:

```diff
 submitForm
   createSession
     persistPrompt
+    expandSkillMention
     launchAgent
```

형식별 예시는 [show-me](../../show-me/SKILL.md)를 참고한다. 별도 HTML 파일을 열어야 하는 형식은 PR 본문에 쓰지 않는다.

call tree는 [calldiff](https://github.com/tanishqkancharla/calldiff)로 추출한 뒤 리뷰에 필요한 부분만 남긴다. 별도 설치 없이 `pnpm dlx`로 실행한다.

```bash
pnpm dlx calldiff@latest diff <base-sha> <head-sha> --file <진입 파일> --max-depth 2
```

출력이 너무 길어지지 않도록 진입점을 지정한다. 라우트 파일처럼 export된 함수가 없으면 `--entry <함수명>`을 쓴다. 출력에서 쿼리 빌더·표준 라이브러리 호출을 제외하고, `+`·`-` 줄과 부모 노드만 남긴다. 위 예시처럼 짧게 정리한다.

## 쓰지 않는 것

- 함수·쿼리·파일 단위로 무엇을 바꿨는지 서술한 구현 설명. diff가 담고 있다.
- 코드가 왜 그렇게 생겼는지에 대한 설명. 코드 주석의 몫이다. 본문에 쓰려던 WHY가 코드에 없으면 본문 대신 주석을 추가한다.
- cherry-pick한 커밋 목록, 작업 도중 겪은 시행착오. 필요하면 커밋 메시지에 둔다.
- 에이전트 세션 링크.

## 기존 PR을 고칠 때

최신 본문을 읽고 에이전트가 쓴 섹션만 이 양식으로 고친다. 다른 사람이 쓴 글과 검증 마커 밖에 있던 기존 글은 보존한다. 오래된 PR의 본문을 이 양식으로 옮기려고 따로 수정하지 않는다.
