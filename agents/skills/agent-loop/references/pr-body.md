# PR 본문

PR 본문은 사람이 읽는다. 리뷰어가 병합해도 되는지, 배포할 때 무엇을 조심할지, 무엇을 정해야 하는지 판단하는 데 필요한 것만 적는다.

에이전트는 PR 본문이 아니라 코드베이스에서 맥락을 얻는다. 코드와 diff, 커밋 메시지로 알 수 있는 내용은 본문에 다시 쓰지 않는다. 예외는 `완료 조건 검증` 섹션과 티켓 연결 줄이다. `verify`·`land`가 이 둘을 읽어 작업을 이어받는다.

## 양식

```markdown
Fixes YOU-000 · base: `main`

## 무엇이 달라지나

<사용자·운영자가 겪는 변화 1~3문장>

## 배포 영향

<마이그레이션·환경 변수·배포 순서·백필. 없으면 "없음">

## 정해야 할 것

- <사람이 골라야 하는 갈림길 — 선택지와 추천>

## 리뷰 포인트

- `<파일 또는 영역>` — <먼저 봐야 하는 이유>

## 범위 밖

- <이번 PR이 하지 않은 것과 이어받을 곳>

<!-- verify:start -->
## 완료 조건 검증
...
<!-- verify:end -->
```

섹션 이름과 순서는 바꾸지 않는다. 이름이 PR마다 다르면 리뷰어가 매번 찾아 읽어야 한다.

## 섹션별 기준

**티켓 연결 줄** — 필수. `Fixes`·`Closes`로 티켓을 연결하고 실제 base를 적는다. 티켓이 없으면 base만 적는다.

**무엇이 달라지나** — 필수. 코드 용어 없이, 기능을 쓰는 사람 입장에서 바뀐 동작을 쓴다. 내부 리팩터링처럼 사용자가 겪는 변화가 없으면 "동작 변화 없음"과 바뀐 이유 한 문장을 쓴다.

**배포 영향** — 필수. 내용이 없어도 "없음"으로 채운다. 섹션이 빠진 PR과 영향이 없는 PR을 구분하기 위해서다. 적을 것:
- 마이그레이션 파일 이름과, 사람이 직접 적용해야 한다는 사실
- 새로 필요한 환경 변수·시크릿과, 설정해야 하는 곳
- 서버와 앱처럼 배포 순서가 있으면 그 순서와 이유
- 백필이나 데이터 정리가 필요하면 대상과 실행 주체

**정해야 할 것** — 있을 때만. 제품 정책·비용·사용자에게 보이는 동작처럼 에이전트가 정하지 않고 보류한 항목이다. 선택지와 추천을 함께 적는다. 팀이 정해야 하는 항목은 프로젝트 지침에 따라 트래커 코멘트 초안도 따로 준비한다.

**리뷰 포인트** — 있을 때만. diff에서 먼저 봐야 할 곳 2~3개와 그 이유다. 코드가 한 일을 서술하는 게 아니라 "여기가 위험하거나 판단이 들어갔다"를 알려 주는 안내다.

**범위 밖** — 있을 때만. 티켓 범위 안인데 하지 않은 것, 발견했지만 손대지 않은 문제를 적는다. 후속 티켓이 있으면 연결한다.

**완료 조건 검증** — [검증과 기록 방법](verification.md)의 형식을 따른다. 근거는 리뷰어가 한 번 읽고 믿을 수 있을 만큼만 쓴다. 재현 방법과 관찰 결과를 적고, 결과를 재사용한 논증이나 내부 식별자 나열은 줄인다.

## 쓰지 않는 것

- 함수·쿼리·파일 단위로 무엇을 바꿨는지 서술한 구현 설명. diff가 담고 있다.
- 코드가 왜 그렇게 생겼는지에 대한 설명. 코드 주석의 몫이다. 본문에 쓰려던 WHY가 코드에 없으면 본문 대신 주석을 추가한다.
- cherry-pick한 커밋 목록, 작업 도중 겪은 시행착오. 필요하면 커밋 메시지에 둔다.
- 에이전트 세션 링크.

## 기존 PR을 고칠 때

최신 본문을 읽고 에이전트가 쓴 섹션만 이 양식으로 고친다. 다른 사람이 쓴 글과 검증 마커 밖에 있던 기존 글은 보존한다. 오래된 PR의 본문을 이 양식으로 옮기려고 따로 수정하지 않는다.
