# 검증하고 PR에 결과 적기

`implement`와 `verify`가 함께 사용하는 규칙이다. `review-round`와 `land`는 이 기록을 읽는다. 자신이 한 작업을 이유로 이전 검증 결과를 새 코드에서도 통과한 것으로 바꾸지 않는다.

## 무엇을 확인했는지 분명히 하기

- 이슈의 `## 완료 조건`을 제한 조건까지 빠뜨리지 않고 읽는다. `Acceptance criteria`·`검수 기준`도 같은 뜻으로 읽는다. 조건이 바뀌거나 추가됐으면 이전 기록만 보고 통과로 처리하지 않는다.
- `충족`은 해당 조건을 모두 확인한 근거가 있을 때, `미충족`은 실제로 기대한 결과가 나오지 않았을 때 쓴다. 근거가 부족하거나 환경 문제로 실행하지 못했거나 이전 결과를 그대로 쓸 수 없으면 `미검증`이다. 타입 체크 통과나 리뷰에서 지적이 없었다는 사실만으로 실제 동작을 증명할 수는 없다.
- 같은 조건을 확인한 기존 테스트, API 요청, 화면 확인 결과는 재사용할 수 있다. 코드, 검사 입력, 의존성, 환경이 여전히 맞는지 확인하고 새로 실행했다고 쓰지 않는다.
- 저장소에 프로젝트 검증 스킬(`.agents/skills/verify-<app>/`)이 있으면 먼저 읽고, 검증할 기능의 메모와 실행 환경 규칙을 따른다.
- 프로젝트 검증 스킬에 doctor가 있으면 첫 조작 전과, 조작이 예상과 다르게 실패한 직후에 실행한다. doctor가 실패한 상태의 결과는 `미충족`이 아니라 `미검증`의 근거다.
- 실행 전에 통과 기준과 [조건별 필수 근거](../../verify/references/routes.md)를 정한다. 기록물은 조건을 판단할 만큼 남기며, 개수를 채우기 위한 중복 촬영은 하지 않는다.
- 최종 기록에는 PR head의 전체 SHA를 적는다. 실행 전후에 `agent-loop/scripts/check-worktree.sh <worktree> <expected-head>`로 worktree에 커밋하지 않은 변경이 없는지와 커밋이 맞는지 확인한다. 실행한 서버·기기·API가 실제로 그 코드와 환경을 사용했는지도 확인한다.
- `implement`는 제품 코드와 새 테스트를 커밋한 뒤 최종 head에서 검증한다. 커밋 전에 실행한 결과는 당시 코드, 테스트, 의존성, 입력이 최종 커밋과 같음을 확인한 경우에만 재사용하고 이유를 적는다. 테스트 뒤 바뀐 코드까지 확인했다고 쓰지 않는다.
- `verify`는 제품 코드를 고치지 않는다. 새 검증 파일과 설정은 임시 디렉터리나 이미 gitignore로 제외된 결과 폴더에 둔다. PR에 넣을 회귀 테스트는 구현 작업에서 반영한 뒤 새 커밋에서 확인한다.
- 검증 중 코드나 head가 달라지면 이전 결과를 그 PR head의 근거로 올리지 않는다. 실제로 확인한 커밋의 결과를 남기고, 변경이 검증에 미친 영향을 다시 살핀다.

## UI 기록물과 완료

- 조건을 확인하고 필수 캡처·영상을 사람이 열어볼 수 있게 전달해야 검증이 끝난다. 텍스트 관찰·접근성 트리만으로 완료하지 않는다.
- 실제 실행한 기록물을 해당 완료 조건에 연결한다. 같은 코드·입력·환경에서 유효한 기록물은 재사용하고, 여러 조건을 보여주는 파일은 함께 참조한다.
- 필수 기록물을 못 남겼다면 확인한 결과와 막힌 이유, 남은 작업을 적고 해당 UI 조건은 `미검증`으로 둔다. 실제 동작이 실패했다면 `미충족`을 유지한다.
- PR 첨부만 막혔다면 검증 결과는 유지하고 로컬 기록물을 제공한다. `PR 첨부 미완료`와 원인을 남긴다. `--no-publish`·로컬 검증은 로컬 파일을 전달하면 된다.

## 기존 결과를 다시 쓸 수 있는지 확인하기

`verify/scripts/verified-head.sh <PR> [<worktree>]`로 기록한 커밋과 PR head를 비교한다.

| 출력 | 뜻 |
|---|---|
| `current <sha>` · exit 0 | 기록한 커밋과 PR head가 정확히 같다. |
| `stale <sha> <n>` · exit 1 | 서로 다른 커밋이다. n은 두 쪽 중 한쪽에만 있는 커밋 수의 합이며 “n 커밋 전”이라는 뜻은 아니다. |
| `missing <이유>` · exit 2 | 기록이 없거나 어느 기록인지 모호하다. 또는 SHA나 원격 상태를 확인할 수 없다. |

merge나 rollback을 했거나 파일 내용이 같더라도 SHA가 다르면 `stale`이다. `current`여도 빠진 항목, 바뀐 완료 조건, 달라진 환경은 따로 확인한다.

- head가 같으면 사용자가 요청한 항목, 환경이 달라진 항목, 실패했거나 확인이 부족했던 항목만 다시 확인한다. 다른 유효한 결과를 얻으려고 같은 검사를 반복하지 않는다.
- head가 바뀌면 항목별로 영향을 살핀다. 확인한 코드, 의존성, 환경이 그대로라는 구체적인 근거가 있으면 이전 결과의 출처와 재사용 이유를 적는다. 영향을 받았거나 확실하지 않은 항목만 다시 실행한다.
- 기록의 SHA만 새 값으로 바꾸지 않는다. 새 head의 모든 조건에 대해 위 판단을 마친 뒤 기록을 갱신한다. 확인이 남은 조건은 미검증으로 두고, 이전 근거의 SHA와 부족한 점을 적는다.

## PR에 결과 적기

PR 본문의 `## 완료 조건 검증` 한 곳에 현재 결과를 적는다. `implement`는 PR을 만들 때 결과를 넣고, `verify`는 같은 섹션을 갱신한다. 모두 충족했다면 `verify`를 다음 필수 단계로 안내하지 않는다.

```markdown
<!-- verify:start -->
## 완료 조건 검증

검증 대상: [<full sha>](https://github.com/<owner>/<repo>/commit/<full sha>) · 환경: <실제 환경>

- [x] <완료 조건 원문> — 충족
  - 근거: <재현 방법·관찰 결과 또는 유효한 기존 근거의 출처. UI는 필수 기록물 첨부>
- [ ] <완료 조건 원문> — 미충족
  - 결과: <기대와 실제 결과>
- [ ] <완료 조건 원문> — 미검증
  - 이유: <실제 장애 또는 남은 확인>
<!-- verify:end -->
```

[evidence-block.mjs](../../verify/scripts/evidence-block.mjs)가 `results.json`으로 위 형식의 본문을 만든다. 게시와 첨부 방법은 필요할 때 [PR에 검증 결과 적기](../../verify/references/publishing.md)를 읽는다.

- 저장 직전에 PR head, 이슈의 완료 조건, PR 본문을 다시 읽는다. 읽은 뒤 본문이 달라졌다면 최신 본문에 결과를 반영한다. 저장 후에도 head와 본문을 확인한다.
- 티켓을 연결하는 줄과 검증 섹션 밖의 글은 그대로 둔다. 마커 밖을 정리하거나 오래된 본문으로 전체를 덮어쓰지 않는다. 검증 섹션이 중복돼 어느 쪽인지 알 수 없으면 게시를 보류한다.
- 사용자가 PR 없이 로컬 검증을 요청했다면 실제 로컬 SHA와 환경으로 보고한다. 열린 PR을 검증했다고 표현하지 않는다.
