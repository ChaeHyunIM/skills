# 검증하고 PR에 결과 적기

`implement`와 `verify`가 함께 사용하는 규칙이다. `land`는 이 기록을 읽고 병합할 코드에도 유효한지 확인한다. 자신이 한 작업을 이유로 이전 검증 결과를 새 코드에서도 통과한 것으로 바꾸지 않는다.

이 문서는 검증 결과의 판정 기준과 기록 방법을 다룬다. 앱 실행·조작 방법과 완료 조건별로 남길 기록물은 저장소의 프로젝트 검증 스킬(`.agents/skills/verify-<app>/`)을 따른다. 먼저 해당 스킬을 읽고 Launch·Doctor·Drive·Evidence·Cleanup의 지침대로 진행한다. 스킬이 없으면 저장소 문서와 코드에서 실행 방법을 찾아 검증하고, `/create-verification-skill`로 만들 수 있다고 사용자에게 알린다. 직접 만들지는 않는다.

## 무엇을 확인했는지 분명히 하기

- 이슈의 `## 완료 조건`을 제한 조건까지 빠뜨리지 않고 읽는다. `Acceptance criteria`·`검수 기준`도 같은 뜻으로 읽는다. 조건이 바뀌거나 추가됐으면 이전 기록만 보고 통과로 처리하지 않는다.
- `충족`은 해당 조건을 모두 확인한 근거가 있을 때, `미충족`은 검증 환경이 정상인데도 기대한 동작이 나오지 않았을 때 쓴다. 근거가 부족하거나 환경·도구 문제로 실행하지 못했거나 이전 결과를 그대로 쓸 수 없으면 `미검증`이다. doctor가 실패한 상태에서 얻은 결과도 `미검증`으로 남긴다.
- 같은 조건을 확인한 기존 테스트, API 요청, 화면 확인 결과는 재사용할 수 있다. 코드, 검사 입력, 의존성, 환경이 여전히 맞는지 확인하고 새로 실행했다고 쓰지 않는다.
- 실제 사용자가 이용하는 경로로 확인한다. 진입 경로가 검증 대상이면 URL이나 deep link로 바로 여는 것으로 대체하지 않는다. 실행 중인 앱에 코드를 주입해 사용자 조작이나 결과를 대신 만들지 않는다.
- 데이터 저장·권한·중복 방지는 화면뿐 아니라 테스트·API 응답·DB에 저장된 데이터로도 확인한다.
- 재시도한 뒤 통과했으면 이유와 횟수를 적는다.
- 코드 품질은 [code-quality](../../code-quality/SKILL.md)에 따라 변경에 해당하는 전문 스킬을 적용해 검증한다. 적용한 스킬과 확인 결과를 검증 기록에 짧게 남긴다.
- 최종 기록에는 PR head의 전체 SHA를 적는다. 검증한 코드가 그 커밋과 같은지, 실행한 서버·기기·API가 실제로 그 코드와 환경을 사용했는지 확인한다.
- `implement`는 제품 코드와 새 테스트를 커밋한 뒤 최종 head에서 검증한다. 커밋 전에 실행한 결과는 당시 코드, 테스트, 의존성, 입력이 최종 커밋과 같음을 확인한 경우에만 재사용하고 이유를 적는다.
- `verify`는 제품 코드를 고치지 않는다. 새 검증 파일과 설정은 임시 디렉터리나 이미 gitignore로 제외된 결과 폴더에 둔다. PR에 넣을 회귀 테스트는 구현 작업에서 반영한 뒤 새 커밋에서 확인한다.
- 검증 중 코드나 head가 달라지면 이전 결과를 그 PR head의 근거로 올리지 않는다. 실제로 확인한 커밋의 결과를 남기고, 변경이 검증에 미친 영향을 다시 살핀다.

## 기록물과 완료

- 프로젝트 검증 스킬이 정한 필수 기록물을 사람이 열어볼 수 있게 전달해야 검증이 끝난다. UI 조건은 텍스트로 적은 관찰 결과나 접근성 트리만으로 검증을 마치지 않는다.
- 실제 실행한 기록물을 해당 완료 조건에 연결한다. 같은 코드·입력·환경에서 유효한 기록물은 재사용하고, 여러 조건을 보여주는 파일은 함께 참조한다.
- 필수 기록물을 못 남겼다면 확인한 결과와 막힌 이유, 남은 작업을 적고 해당 조건은 `미검증`으로 둔다. 실제 동작이 실패했다면 `미충족`을 유지한다.
- PR 첨부만 막혔다면 검증 결과는 유지하고 로컬 기록물을 제공한다. `PR 첨부 미완료`와 원인을 남긴다. `--no-publish`·로컬 검증은 로컬 파일을 전달하면 된다.

## 기존 결과를 다시 쓸 수 있는지 확인하기

`agent-loop/scripts/verified-head.sh <PR> [<worktree>]`로 기록한 커밋과 PR head를 비교한다.

| 출력 | 뜻 |
|---|---|
| `current <sha>` · exit 0 | 기록한 커밋과 PR head가 정확히 같다. |
| `stale <sha> <n>` · exit 1 | 서로 다른 커밋이다. n은 두 쪽 중 한쪽에만 있는 커밋 수의 합이며 “n 커밋 전”이라는 뜻은 아니다. |
| `missing <이유>` · exit 2 | 기록이 없거나 어느 기록인지 모호하다. 또는 SHA나 원격 상태를 확인할 수 없다. |

merge나 rollback을 했거나 파일 내용이 같더라도 SHA가 다르면 `stale`이다. `current`여도 빠진 항목, 바뀐 완료 조건, 달라진 환경은 따로 확인한다.

- head가 같으면 사용자가 요청한 항목, 환경이 달라진 항목, 실패했거나 확인이 부족했던 항목만 다시 확인한다.
- head가 바뀌면 항목별로 영향을 살핀다. 확인한 코드, 의존성, 환경이 그대로라는 구체적인 근거가 있으면 이전 결과의 출처와 재사용 이유를 적는다. 영향을 받았거나 확실하지 않은 항목만 다시 실행한다.
- 기록의 SHA만 새 값으로 바꾸지 않는다. 새 head의 모든 조건에 대해 위 판단을 마친 뒤 기록을 갱신한다. 확인이 남은 조건은 미검증으로 두고, 이전 근거의 SHA와 부족한 점을 적는다.

## PR에 결과 적기

PR 본문의 `## 완료 조건 검증` 한 곳에 현재 결과를 아래 형식으로 직접 적는다. `implement`는 PR을 만들 때 결과를 넣고, `verify`는 같은 섹션을 갱신한다. 모두 충족했다면 `verify`를 다음 필수 단계로 안내하지 않는다.

```markdown
<!-- verify:start -->
## 완료 조건 검증

검증 대상: [<full sha>](https://github.com/<owner>/<repo>/commit/<full sha>) · 환경: <실제 환경>

- [x] <완료 조건 원문> — 충족
  - 근거: <재현 방법·관찰 결과 또는 유효한 기존 근거의 출처>
- [ ] <완료 조건 원문> — 미충족
  - 결과: <기대와 실제 결과>
- [ ] <완료 조건 원문> — 미검증
  - 이유: <실제 장애 또는 남은 확인>
<!-- verify:end -->
```

`verified-head.sh`가 이 제목과 `검증 대상:` 줄을 읽으므로 둘 다 섹션 안에 한 번만 둔다. 기록물은 해당 항목 바로 아래에 넣는다.

- 기존 PR은 저장 직전에 head, 이슈의 완료 조건, 본문을 다시 읽고 마커 사이만 바꾼다. 티켓을 연결하는 줄과 마커 밖의 글은 공백까지 그대로 둔다. `gh pr edit <PR> --body-file <file>`로 저장한 뒤 head와 본문을 다시 확인한다.
- 검증 섹션이나 마커가 중복돼 어느 쪽을 수정해야 할지 알 수 없으면 임의로 지우지 않고 게시를 보류한다. 다른 사람도 편집 중이면 작성한 결과는 보관하고 PR 저장만 보류한다.
- 파일을 첨부할 때는 `gh pr edit --help`로 `--attach` 지원 여부를 확인한다. 본문에서 `![이름](./상대경로)`로 참조하고 같은 파일을 `--attach`로 넘긴다. 파일은 cwd 안에 있어야 하고 경로에 공백이 없어야 한다. 파일당 최대 10 MB까지 첨부할 수 있다. 영상은 별도 줄에 첨부해야 플레이어로 표시된다. 재생 호환성을 위해 H.264 MP4를 권장한다.
- 변경 전후 영상을 나란히 보여 줘야 할 때만, 두 파일을 `--attach`한 임시 코멘트를 올려 `https://github.com/user-attachments/assets/...` 주소를 얻고 HTML 표의 `<video src>`에 넣는다. 게시된 본문에서 재생을 확인한 뒤 임시 코멘트를 지운다.
- 첨부가 막히면 PR에는 결과·재현 방법·`PR 첨부 미완료: <원인>`을 적고, 채팅으로 로컬 기록물을 전달한다. PR에 로컬 경로를 남기거나 공개 이미지 호스트에 대신 올리지 않는다.
- 사용자가 PR 없이 로컬 검증을 요청했다면 실제 로컬 SHA와 환경으로 보고한다. 열린 PR을 검증했다고 표현하지 않는다.
