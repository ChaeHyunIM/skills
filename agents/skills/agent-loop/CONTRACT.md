# agent-loop 공유 규약

`to-tickets` · `implement` · `verify` · `review-round` · `land`의 공통 계약이다. 시작할 때 이 파일을 읽고, 아래 reference는 해당 작업에 필요한 것만 읽는다. 이 루프의 기본 프로젝트 프로필은 doko다.

## 완료와 권한

- `to-tickets`는 승인된 완료 조건·부모·의존 관계를 갖춘 티켓을 발행한다.
- `implement`는 구현, 필요한 검증, 수정, PR의 검증 기록까지 끝낸다. 모두 확인됐으면 별도 `verify` 호출은 필요 없다.
- `verify`는 남은 조건, 바뀐 코드·환경, 독립 확인 요청을 검증한다. 유효한 기존 근거를 재사용하며 제품 코드는 수정하지 않는다.
- `review-round`는 명시 호출당 읽기 전용 Claude·Codex 리뷰를 각각 한 번 실행하고 바깥 루프가 수정·기각·보류를 처리한다. 유료 엔진의 자동 기동·재시도는 하지 않는다.
- `land`는 그 실행에서 사용자가 지명하거나 확인한 PR만 머지한다. 호출은 정상 병합의 승인이다. 승인 범위를 벗어난 변경이나 미충족·미검증 조건은 구체적인 결과를 제시한 뒤 확인한다.

## 기록과 상태

이슈가 `## 완료 조건`을 소유한다. PR 본문의 `## 완료 조건 검증` 한 곳에 `implement`와 `verify`가 실제 근거를 기록한다. 동시에 편집하지 않고, 저장 직전에 최신 본문을 읽고 저장 뒤 확인한다. 이슈 체크박스는 `land`만 바꾼다. 머지 승인은 검증 충족을 뜻하지 않는다.

검증 기록의 `current`는 기록한 커밋과 PR head가 정확히 같다는 뜻이다. merge 커밋에도 예외가 없다. 기록 안의 항목별 근거·환경·최신 완료 조건은 따로 대조한다. `current` 자체는 모든 조건의 충족을 뜻하지 않는다.

| 상태 | 의미 | 종료·재개 |
|---|---|---|
| `ready` | 스펙 준비 완료. 블로커가 열려 있어도 유지 | 실제 의존이 풀리면 implement |
| `in-progress` | 구현 작업 중 | PR과 검증 결과를 준비하면 awaiting-review |
| `awaiting-review` | 사람이 판단할 수 있는 PR | verify·review-round·land 선택 가능 |
| `in-review` | 리뷰 라운드 실행 중 | 정상 완료 또는 엔진 실패 후 실행 종료가 확인되면 awaiting-review; 결정·충돌이 남으면 blocked |
| `blocked` | 필요한 결정·환경 복구·base 충돌을 기다림 | 구현·정책은 implement, 기록으로 확인되는 base 충돌만이면 사용자 지명으로 land |

- 트래커에 루프 상태 표식은 정확히 하나다. 바꾼 뒤 읽어서 확인한다. PR draft 여부나 별도 상태 파일을 두 번째 상태 기록으로 쓰지 않는다.
- 리뷰 엔진이 시작하지 못했거나 모두 종료했다면 `in-review`를 남기지 않는다. 종료 여부가 불명확하면 먼저 확인하며 다른 쓰기 작업을 시작하지 않는다.
- 검증 환경만 부족하면 실행한 결과와 미검증 이유를 남긴다. 나머지 검증·작업은 계속한다.

## 경계

- 제품 정책·비용·승인된 의도를 새로 정해야 하면 영향을 받는 부분만 보류한다. 합리적으로 보인다는 이유로 서비스 규칙을 만들지 않는다.
- 팀에 결정을 요청하는 글은 초안을 승인받고 게시한다. 멘션 없는 개발 기록과 리뷰 라운드 코멘트는 프로젝트의 예외 규칙을 따른다. 기존 승인이 정확히 해당 내용을 포함하면 다시 묻지 않는다.
- base 브랜치에 커밋·push하지 않고, force-push하지 않는다. 로컬 변경·전용 커밋은 확인하고 보존한다.
- DB·마이그레이션·살아 있는 기능 삭제는 프로젝트 지침의 경계를 그대로 따른다.
- 실제 사용 가능한 plugin·MCP·CLI를 쓴다. 필요한 기능이 없으면 그 기능에 의존하는 쓰기만 멈춘다. 독립적인 조사·초안·검증은 계속하며, 상태·관계를 본문으로 흉내 내거나 성공을 지어내지 않는다.
