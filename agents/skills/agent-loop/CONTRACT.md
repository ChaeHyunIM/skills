# agent-loop 공유 규칙

`to-tickets` · `implement` · `verify` · `land`를 사용할 때 함께 지키는 규칙이다. 시작할 때 이 문서를 읽고, 자세한 설명은 필요한 작업에서만 찾아본다.

프로젝트별 설정과 실행 방법은 다음 위치에서 확인한다.

- 검사 명령: 저장소 지침(`AGENTS.md` 등)
- worktree 설정: 저장소의 `.claude/agent-loop/config`
- 앱 실행과 검증 방법: 저장소의 프로젝트 검증 스킬(`.agents/skills/verify-<app>/`)

## 스킬별 역할

| 스킬 | 하는 일 |
|---|---|
| `to-tickets` | 승인된 목표를 티켓으로 만들고 완료 조건, 상위 티켓, 먼저 끝나야 할 작업을 연결한다. |
| `implement` | 구현하고 실제 동작과 `code-quality`에 따른 코드 품질을 검증·수정한 뒤 PR에 결과를 적는다. 필요한 검증이 모두 끝났으면 별도 `verify` 호출은 필요 없다. |
| `verify` | 아직 확인하지 못한 조건을 검증하거나, 코드·환경이 바뀌었거나 사용자가 별도 확인을 요청한 항목을 다시 확인한다. 그대로 쓸 수 있는 기존 결과는 재사용하며 제품 코드는 고치지 않는다. |
| `land` | 이번 실행에서 사용자가 지정하거나 확인한 PR을 머지한다. 요청대로 병합할 수 있으면 추가 승인 없이 진행한다. 요청에 없던 변경이나 남은 검증이 있으면 구체적인 내용을 보여 주고 확인한다. |

기본 흐름은 `to-tickets → implement → land`다. `implement`에서 실제 동작과 코드 품질을 검증하고, 남은 확인이나 재검증이 필요할 때 `verify`를 쓴다.

사용자 흐름 전체의 리뷰는 사용자가 시점을 정한다. 기준 이슈에서 범위를 찾고 결과를 PR에 기록하려면 [review-flow](../../../claude/skills/review-flow/SKILL.md)를 호출한다. 발견한 문제는 필요한 구현 작업으로 가져와 수정하고 검증한다.

## 완료 조건과 검증 결과를 적는 곳

완료 조건은 이슈의 `## 완료 조건`에 적는다. 검증 결과는 PR 본문의 `## 완료 조건 검증` 한 곳에 적고, `implement`와 `verify`가 함께 사용한다. 두 작업이 동시에 본문을 고치지 않는다. 저장 직전에 최신 본문을 읽고, 저장한 뒤에도 결과를 확인한다.

이슈의 완료 조건 체크박스는 `land`만 바꾼다. 사용자가 머지를 승인했어도 확인하지 못한 조건을 완료로 표시하지 않는다.

이 문서에서 PR의 `head`는 PR에 담긴 마지막 커밋, `base`는 PR을 합칠 대상 브랜치를 뜻한다. 검증 기록의 `current`는 기록한 커밋과 PR head가 정확히 같다는 뜻이다. merge 커밋에도 예외가 없다. `current`라도 빠진 조건이나 달라진 환경이 있는지 따로 확인해야 한다.

## 작업 상태

| 상태 | 뜻 | 다음 작업 |
|---|---|---|
| `ready` | 스펙 작성 완료. 선행 작업이 남아 있어도 유지한다. | 선행 작업이 끝나면 implement |
| `in-progress` | 구현 중 | PR과 검증 결과가 준비되면 awaiting-review |
| `awaiting-review` | 사람이 PR과 검증 결과를 보고 판단할 수 있음 | 남은 확인은 verify, 병합은 land |
| `blocked` | 사람의 결정, 환경 복구 또는 base 충돌 해결을 기다림 | 구현·정책 문제는 implement. 기록상 base 충돌만 남았으면 사용자가 지정해 land |

- 트래커에는 현재 상태를 나타내는 라벨을 하나만 남긴다. 바꾼 뒤 다시 읽어서 확인한다. PR의 draft 여부나 별도 파일에 같은 상태를 중복해서 기록하지 않는다.
- 검증 환경이 부족하면 실행한 결과와 확인하지 못한 이유를 적는다. 영향받지 않는 검증과 작업은 계속한다.

## 사람이 결정해야 할 일과 작업 중 지킬 규칙

- 제품 정책, 비용, 사용자가 승인한 목표를 새로 정해야 하면 그 부분만 보류한다. 답이 합리적으로 보여도 에이전트가 서비스 규칙을 대신 정하지 않는다.
- 팀에 결정을 요청하는 글은 초안을 승인받은 뒤 올린다. 멘션 없는 개발 기록은 프로젝트의 예외 규칙을 따른다. 같은 내용으로 이미 승인받았다면 다시 묻지 않는다.
- base 브랜치에 커밋하거나 push하지 않고, force-push하지 않는다. 로컬 변경과 아직 원격에 올리지 않은 커밋을 확인하고 보존한다.
- DB 작업, 마이그레이션, 서비스 중인 기능 삭제는 프로젝트 지침을 따른다.
- 타입 체크가 통과했거나 리뷰 지적이 없다는 이유로 실제 동작까지 확인했다고 쓰지 않는다.
- 검증을 통과시키려고 assertion이나 완료 조건을 느슨하게 바꾸지 않는다. 실패한 결과와 결정이 필요한 내용을 보고한다.
- 토큰, 쿠키, 인증 정보가 담긴 query parameter, storage-state, 환경 설정값, 사용자 식별 정보는 PR·이슈·채팅에 게시하지 않는다.
- 실제로 사용할 수 있는 plugin·MCP·CLI를 쓴다. 필요한 기능이 없으면 그 기능에 의존하는 변경만 보류한다. 나머지 조사·초안·검증은 계속하되, 트래커 기능 대신 본문에 상태나 관계를 적거나 하지 못한 일을 했다고 쓰지 않는다.

## 글을 쓰는 방식

사람에게 남기는 글은 한국어로, 옆자리 동료에게 설명하듯 쓴다. 누가 무엇을 해야 하는지 드러내고, 설명이 필요한 조건은 문장을 나눠 쓴다. 명령어·설정값·정확한 기술 이름은 유지한다. 평범한 동작을 설명할 때는 평소 대화에서 쓰는 말을 고른다.

진행 보고에는 확인한 사실, 남은 일, 필요한 결정만 짧게 적는다. 작업용 체크리스트를 응답에 그대로 반복할 필요는 없다.
