# 리뷰 진행 방법

Codex와 Claude에서 같은 순서로 진행한다. 리뷰를 실행하고 기다리는 방법만 각 환경의 문서를 따른다. [공유 규칙](../../CONTRACT.md), [트래커 규칙](../../references/tracker.md), [작업 폴더와 커밋 절차](../../references/workspace.md)를 함께 적용한다.

## 리뷰 준비

1. 티켓과 연결된 PR, 최신 완료 조건, 기존 검증 결과를 읽는다. 다른 구현이나 리뷰가 진행 중이면 동시에 브랜치를 고치지 않는다. 열린 PR이 없으면 없다고 보고한다.
2. `agent-loop/scripts/sync-worktree.sh <worktree> <branch>`로 로컬 작업이 없는지 확인하고 원격의 최신 커밋을 가져온다. 기존 로컬 작업은 보존한다. 원격 PR head와 worktree HEAD가 같은지 확인한다.
3. 리뷰할 HEAD를 `ROUND_BASE`, PR base를 fetch해서 얻은 커밋 SHA를 `COMPARISON_REF`로 정한다. 실제 base 브랜치 이름도 기록한다. 리뷰 결과를 처리할 때는 이슈의 완료 조건과 PR 본문도 함께 대조한다.
4. [리뷰 실행 옵션](arguments.md)의 스크립트로 이번 호출의 모델과 effort를 정하고 로그인 등 실행 준비를 확인한다. 실패하면 리뷰를 시작하지 않는다. 기존 정책 결정이나 충돌 보류는 그대로 두고, 시작하지 않은 리뷰를 실행 중 상태로 표시하지 않는다.
5. 기존 라운드 번호 중 가장 큰 값에 1을 더해 K를 정하고 `in-review`로 바꾼다. 이번 실행의 임시 폴더를 새로 만든다. [Codex](codex-runtime.md) 또는 [Claude](claude-runtime.md)의 실행 방법으로 두 리뷰어를 시작하고 모두 끝날 때까지 기다린다.

## 결과 확인과 실패 처리

두 리뷰가 끝났는지, worktree와 원격 PR의 head·base가 처음 정한 커밋 그대로인지 확인한다. `agent-loop/scripts/check-worktree.sh <worktree> <ROUND_BASE>`로 커밋하지 않은 변경도 확인한다.

```bash
bash ~/.agents/skills/agent-loop/review-round/scripts/extract-findings.sh <scratch>/review-<N>-r<K>.jsonl
bash ~/.agents/skills/agent-loop/review-round/scripts/codex-review.sh extract <scratch>/codex-review-<N>-r<K>.json "$ROUND_BASE" "$CODEX_MODEL" "$EFFORT"
```

- Claude 추출 명령의 종료 코드가 0이면 정해진 형식의 결과를 얻은 것이다. 2이면 일반 텍스트에서 결과를 추출한 상태(degraded), 3이면 쓸 수 있는 결과가 없는 상태다. Codex는 종료 코드 0만 사용하며 일반 텍스트로 대신하지 않는다.
- 실행 실패, 시간 초과, 잘못된 결과, 리뷰 대상 변경이 있으면 한쪽 리뷰만 보고 수정 여부를 결정하지 않는다. 원본 결과와 오류 출력을 보존하고 자동 재실행하지 않는다.
- 두 리뷰가 모두 끝났고 정책 결정이나 충돌이 남지 않았으면, 실패했더라도 `awaiting-review`로 돌리고 실패 내용을 기록한다. 프로세스가 종료됐는지 불명확하면 먼저 확인한다. 실패 기록을 남기려고 `in-review`를 유지하지 않는다.

## 지적을 모으고 수정하기

- 원본의 `short_summary`는 요약 표에, `failure_scenario`는 처리 이유에 사용한다. Claude의 `verdict`는 이번 실행에서 실제로 제공한 경우만 쓴다. Codex의 `test_gaps`·`residual_risks`·`overall_assessment`는 리뷰의 한계 설명에 쓰고 지적 수에 추가하지 않는다.
- 같은 위치에서 같은 실패를 지적한 경우만 하나로 합치고 출처를 `Claude+Codex`로 쓴다. 실패 상황이 다르면 따로 남긴다. 합친 목록 순서대로 번호를 붙인다.
- 완료 조건마다 구현과 기존 검증 결과를 확인한다. 구현이 빠졌다면 출처를 `완료 조건`으로 적는다. 코드가 없는 경우 파일이나 줄 번호를 만들어 내지 않는다. 검증 근거만 부족한 항목은 확인이 남았다고 적고 리뷰어의 지적 수에 섞지 않는다.
- 모은 지적과 처리 결과는 `<scratch>/review-<N>-r<K>.findings.json`에 적는다. 리뷰어의 원본 결과는 그대로 보존한다.

| 처리 | 기준 |
|---|---|
| 반영 | 근거로 확인한 버그, 타입 오류, 프로젝트 규칙 위반이다. 작업 범위 안에서 고치고 필요한 검사를 한다. |
| 기각 | 지적이 사실과 다르다. 그렇게 판단한 근거와 코드 위치 또는 실행 결과를 남긴다. |
| 보류 | 제품 정책, 비용, 승인받지 않은 구조 변경, 마이그레이션 등 사람이 결정할 일이다. 코드로 대신 결정하지 않고 선택지와 추천을 적는다. |

보류한 항목 중 개발자가 결정할 일과 팀이 함께 결정할 일을 구분한다. 코드를 바꿨으면 공통 절차대로 주석을 정리하고 검사한 뒤 커밋·push한다. 관련된 테스트를 실행하되 같은 코드와 입력에서 통과한 검사를 이유 없이 반복하지 않는다.

## 최신 base 반영과 검증 기록 확인

- 최신 PR base를 fetch해서 작업 브랜치에 merge한다. base 변경이 검사할 코드나 입력에 영향을 줬으면 이미 통과한 타입 체크도 다시 한다.
- base 충돌이 생기면 merge를 중단하고 `blocked`로 남긴다. 충돌만 남았으면 사용자가 지정해 `land`로 이어갈 수 있다. 정책 결정이나 구현 문제도 있으면 먼저 해결해야 한다.
- 마이그레이션 순서는 파일별로 살피고 사람이 판단할 부분을 보류 항목에 넣는다. 생성과 적용은 프로젝트 지침을 따른다.
- `verified-head.sh`로 기존 검증 기록을 확인한다. head가 바뀌었는데 검증했다고 기록을 덮어쓰지 않는다. 이번 라운드에서 실행한 검사는 라운드 코멘트에 적고, PR 본문의 검증 결과는 `implement`·`verify`가 실제 근거를 확인해 갱신한다.

## 결과 게시와 마무리

마지막 push 뒤 `ROUND_BASE..ROUND_HEAD` 범위를 계산하고 [리뷰 결과 코멘트](round-comment.md) 형식으로 PR 코멘트 하나를 남긴다. 본문은 파일로 작성해 `--body-file`로 전달한다. 중단된 작업을 이어가는 경우 같은 라운드가 이미 게시됐는지 확인해 중복을 피한다.

- 결정할 항목, base 충돌, 해결하지 못한 구현 오류나 검사 실패가 있으면 `blocked`, 없으면 `awaiting-review`로 바꾼다. 티켓에는 PR 코멘트 링크를 남긴다.
- 팀이 결정할 항목은 [팀에 결정을 요청하는 코멘트](team-comment.md)에 따라 짧은 초안을 만들고 승인받아 올린다. 승인을 기다리는 동안 다른 라운드 작업은 마친다.
- 채팅에는 결과 링크, 반영·기각·보류 수, 실제 검증 상태, 필요한 결정만 보고한다. PR에 적은 결정의 뜻을 바꾸지 않는다. 매번 불필요한 다음 명령 목록을 붙이지 않는다.

사용자의 한 번 호출로 한 라운드만 실행한다. 리뷰를 추가로 시작하거나 머지하지 않는다.
