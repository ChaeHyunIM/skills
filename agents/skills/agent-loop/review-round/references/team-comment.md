# 팀 보류 코멘트 — 비개발자가 읽는 별도 코멘트

라운드의 보류에는 두 종류가 섞인다.

- **개발 보류** — 답을 개발자가 코드로 낸다. 마이그레이션 타이밍, 구조 선택, 성능 트레이드오프.
  PR 코멘트의 보류 섹션에서 끝난다. 티켓에는 포인터 한 줄뿐이다.
- **팀 보류** — 답이 «제품이 뭘 하느냐» 다. 정책·운영 규칙·비용·사용자에게 보이는 동작.
  기획·디자인·운영도 결정에 참여하고, 그 사람들은 PR 을 열지 않는다.

**팀 보류가 1건 이상이면 그 항목만 다시 써서 티켓에 별도 코멘트로 올린다.** PR 코멘트가 원본이고
이 글은 다른 독자를 위한 번역본이다. 개발 보류는 여기 옮기지 않는다.

## 게시 전 승인이 필수다

이 코멘트는 팀원이 읽는 글이므로 **초안을 채팅에 전문 그대로 내고, 사람의 승인을 받은 뒤에만**
`"$TRACKER" comment` 로 올린다. 승인 없이 게시하지 않는다. 승인을 기다리는 동안 티켓 상태는
`blocked` 로 이미 내려가 있고, PR 코멘트도 이미 올라가 있다 — 막히는 것은 이 한 건뿐이다.

## 쓰는 법

사용자가 손대지 않고 그대로 올릴 수 있어야 한다. 고쳐 써야 하면 실패한 초안이다.

- **짧게.** 항목 하나에 5~6줄. 전체가 화면 하나를 넘지 않는다.
- **말하듯이.** 옆자리 동료에게 설명하는 문장. 라벨 나열, 굵은 글씨 남발, 표 금지.
- **코드를 지운다.** `path:line`, 타입 이름, 함수명, HTTP 상태 코드는 빼고 사용자가 겪는 일로 쓴다.
  («23505 가 500 으로 샌다» → «이미 신청한 미션을 또 누르면 오류 화면이 뜬다»)
- **기술 판단은 미리 채운다.** 팀이 «그거 되나요» 를 되묻지 않게, 각 선택지에 «되는지 · 얼마나 걸리는지»
  를 개발자 답으로 한 마디씩 붙인다.
- **선택지·추천·필요한 결정 3요소**는 PR 코멘트와 같이 그대로 유지한다. 선택지 없는 글은 질문이 아니다.

## 형식

```markdown
리뷰하다가 팀이 정해야 할 게 <c>건 나왔습니다. 개발 쪽 판단은 PR 에 정리해 뒀고([링크]), 여기엔 정책만 옮깁니다.

**1. <한 줄 제목>**
지금은 <현재 동작>. <무엇이 애매한지 한 문장>.
- ⓐ <선택지> — <사용자에게 뭐가 달라지나> (개발: <바로 됨 / 반나절 / 마이그레이션 필요>)
- ⓑ <선택지> — <사용자에게 뭐가 달라지나> (개발: <…>)
추천은 ⓑ. <한 줄 근거>.

**2. …**

정해주시면 반영하겠습니다.
```

결정은 이 코멘트의 답글이 아니라 다음 `implement <N>` 지시로 돌아온다. 답글이 달려도 이 코멘트를
고쳐 쓰지 않는다 — 결정 이력은 티켓에 그대로 남는 게 낫다.
