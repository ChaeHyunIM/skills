# 팀에 결정을 요청하는 코멘트

리뷰에서 보류한 일 중 누가 결정해야 하는지 구분한다.

- 개발자가 결정할 일은 마이그레이션 시점, 코드 구조, 성능과 구현 복잡도 사이의 선택 등이다. PR 코멘트의 보류 섹션에 적고 티켓에는 그 링크 한 줄만 남긴다.
- 팀이 함께 결정할 일은 제품 정책, 운영 규칙, 비용, 사용자에게 보이는 동작이다. 기획·디자인·운영도 참여하며 이 사람들은 PR을 열어보지 않는다.

팀이 결정할 항목이 하나라도 있으면 그 내용만 비개발자가 읽을 수 있게 다시 써서 티켓에 별도 코멘트로 올린다. 결정의 원본은 PR 코멘트이며 선택지와 추천의 뜻은 같아야 한다. 개발자만 결정할 항목은 옮기지 않는다.

## 초안을 승인받은 뒤 게시하기

팀원이 읽을 글이므로 채팅에 전체 초안을 보여 주고 사람의 승인을 받은 뒤에만 티켓에 올린다. 이때 티켓은 이미 `blocked`이고 PR 코멘트도 게시된 상태다. 승인 대기로 남는 일은 이 코멘트 게시뿐이다.

## 동료에게 설명하듯 쓰기

사용자가 손대지 않고 그대로 올릴 수 있어야 한다. 다시 고쳐 써야 한다면 초안이 충분히 정리되지 않은 것이다.

- 항목 하나는 5~6줄로 짧게 쓰고 전체는 한 화면 안에 들어오게 한다.
- 옆자리 동료에게 설명하듯 쓴다. 라벨만 나열하거나 굵은 글씨를 남발하지 않고 표는 쓰지 않는다.
- `path:line`, 타입·함수 이름, HTTP 상태 코드 대신 사용자가 겪는 일을 설명한다. 예를 들어 “중복 신청 오류가 500 응답으로 반환된다”는 “이미 신청한 미션을 또 누르면 오류 화면이 뜬다”로 쓴다.
- 팀이 “그 방법이 가능한가요?”를 다시 묻지 않도록 각 선택지에 구현 가능 여부와 예상 작업량을 짧게 덧붙인다.
- PR에 적은 선택지, 추천, 필요한 결정을 그대로 유지한다. 선택지 없이 판단을 떠넘기지 않는다.

## 코멘트 형식

```markdown
리뷰 중 팀에서 정해야 할 내용이 <c>건 나왔습니다. 개발 관련 내용은 [PR 코멘트](<링크>)에 정리했고, 함께 결정할 내용을 여기에 적었습니다.

**1. <제목>**
지금은 <현재 동작>. <아직 정하지 못한 부분 한 문장>.
- ⓐ <선택지> — <사용자에게 달라지는 점> (개발: <바로 가능 / 반나절 / 마이그레이션 필요>)
- ⓑ <선택지> — <사용자에게 달라지는 점> (개발: <…>)
추천은 ⓑ입니다. <이유 한 줄>.

**2. …**

정해 주시면 반영하겠습니다.
```

결정은 다음 `implement <N>` 지시로 받아 반영한다. 티켓에 답글이 달렸어도 이 코멘트를 고쳐 쓰지 않는다. 어떤 선택지를 제시했고 무엇을 결정했는지 기록이 남아야 한다.
